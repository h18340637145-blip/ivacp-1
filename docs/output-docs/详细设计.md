## 2. 客户端 Store 与数据模型

`lib/db/schema.ts` 定义 Dexie schema。Jira 侧核心实体为 `RuleGroup`、`FilterTask`、`FilteredIssueSnapshot`、`IssueProcessTask`、`IssueProcessResult`、`IssueAnalysisHistory`、`IssueValidationRun`、`IssueReviewSample` 与 `LearningMemory`。飞书侧核心实体为 `MeegleAssignment`、`MeegleFilterAudit`、`MeegleFilterTask`、`MeegleFilteredIssueSnapshot`、`MeegleIssueSnapshot`、`MeegleProcessTask`、`MeegleProcessResult`、`MeegleAnalysisHistory` 与 `MeegleValidationRun`。

| Store | 关键职责 |
|---|---|
| `useRuleGroupStore` | 规则组本地 CRUD、排序、导入导出。 |
| `useFilterTaskStore` | Jira 筛票请求、超时控制和快照。 |
| `useProcessTaskStore` | Jira 处理、结果、历史、回填与状态流转。 |
| `useRuleGroupWorkflowStore` | 并行筛选和按来源构建处理派发计划。 |
| `meegleFilterTaskStore` | 飞书筛选任务顺序、审计和完成状态。 |
| `useMeegleAssignmentStore` | 自动 / 人工分配及其来源边界。 |
| `useMeegleProcessStore` | 飞书快照、处理、结果恢复、历史、复核和回填。 |
| `useValidationStore` | 校验运行与人工改判。 |

## 3. 处理流水线

`/api/issues/process` 接收规范化后的工单、规则组、附件、历史样本和运行标识，按以下顺序执行：

1. 创建运行目录，记录 `PREPARING`。
2. 分类和下载 Jira 或飞书附件，记录 `DOWNLOADING`。
3. 解压 ZIP / 7z 等包，记录 `UNPACKING`。
4. 解析 `.asc` / `.blf`，抽取信号 token，映射配置和 Property ID，输出 `signals.json`、`signals_id.json`、`extract.md`、持续区间摘要和 `traceData`，记录 `PARSING`。
5. 生成 `evidence-packet.json`，加入评论、OCR、日志与可信证据，调用文本 / 图片模型，记录 `MODEL_INFERENCE`。
6. 生成最终回复与可选版本信息，记录 `GENERATING_REPLY`。
7. 返回结果与运行引用，记录 `SAVING_RESULT`；成功后可异步归档当前日志。

`pipeline-metrics.json`、`stages.json`、`pipeline.log` 和最终回复等运行文件用于排障与离线评测。前端只能消费已提取的 `traceData`；`candidateSources` 与未匹配 token 仅供审计。

### 3.1 飞书项目接入契约

`/api/meegle/analyze` 接收 `workItemId`、`workItemName`、`description`、`projectName`、可选状态、规则组 Prompt、CAN 基础路径、车型文件映射、规则组 ID / 名称、`runId`、`projectKey`、`workItemTypeKey` 与 `rawData`。路由将其转换为共享处理请求：`source: "meegle"`、`runId: task.id`，并把规则组配置及原始快照一并传入 `/api/issues/process`。

结果持久化在客户端外层成功响应之后完成：`useMeegleProcessStore` 写入 `MeegleIssueSnapshot`、`MeegleProcessTask`、`MeegleProcessResult` 和需要时的 `MeegleAnalysisHistory`。因此服务端运行成功但外层响应超时、失败或被归档阻塞时，不能视为浏览器结果已保存；诊断应依次检查 API 响应、IndexedDB 和结果详情读取。

## 4. 复核、校验与幂等

AI 复核使用历史错误样本和证据指纹作为建议输入。证据接地率使用 `evidence_packet`、`can_signal_summary`、`can_trace_extracted_result`、`signals_id` 与 `extract` 等具名来源；缺失证据会进入审计，校验结果不阻断人工决定。

飞书评论携带结果标记以避免重复写入。评论成功后才尝试可选 workflow；失败只保存流转失败。经办人修改的授权链包含当前详情凭据、目标绑定授权和写前二次读取，检测到并发变化时要求刷新。Jira 与飞书的人工复核都是外部写入的门禁。

## 5. 运行配置与安全约束

| 配置类别 | 示例变量 / 文件 | 约束 |
|---|---|---|
| Jira | `JIRA_SERVER`、`JIRA_USERNAME` | 凭据仅服务端使用。 |
| 模型 | `IMAGE_MODEL`、校验模型与 API Key | 文本、图片和校验模型可独立配置。 |
| Docupedia | `ENABLE_DOCUPEDIA`、超时 / 重试配置 | 仅异步归档当前运行。 |
| 飞书 | `MEEGLE_ATTACHMENT_PLUGIN_API_URL`、CLI 配置 | 插件不可用时回退评论上下文；不得泄露 Jira 凭据。 |
| 终端 | `REMOTE_SHELL_TARGETS_JSON`、Gateway host / port | 认证材料不返回浏览器，目标必须在白名单。 |
| 项目配置 | `docs/project.json` | 描述终端项目、分支和 repo 路径。 |

`lib/terminal/command-guard.ts` 对交互式命令进行风险评估；配置恢复操作只接收 `tools/json/config_*.json`。artifact 路由限制真实路径、白名单和响应大小，防止路径穿越及大文件直接暴露。

## 6. 验证入口

项目通过 TypeScript 检查、前端与 Store 回归脚本、飞书生命周期 / 附件插件检查、Docupedia 归档检查、OpenAPI 检查、CAN 图静态守卫和准确率评测维护关键边界。执行 Node 命令前应加载本地环境，例如先运行 `source ~/.bashrc`，并使用 Node 20 运行时。
