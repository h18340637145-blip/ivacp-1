  - 从文件应用：导入模板 JSON。
- **版本**：同一 `templateKey` 重复发布时由服务端递增版本；配置与最新版完全相同不生成新版本。模板标识已被他人占用时拒绝（管理员可更新他人模板，作者保持不变）。
- **应用**：应用总是创建一个新规则组「名称（模板 vN）」，不覆盖已有规则组，因此没有多人同时编辑的冲突；创建规则组仍是管理员权限，普通成员可发布、浏览、下载。应用后请核对 CAN 配置路径。每次从团队库应用，服务端累计应用次数。
- **删除**：仅作者或管理员，软删除模板的全部版本。
- 需要服务端配置 `MYSQL_URL`；未配置时团队库提示不可用，文件导入导出仍可用。
- **统计报告**：统计弹窗新增「复制统计报告」，生成 Markdown（来源表 + 团队模式下的成员明细），可粘贴到飞书 / Docupedia / 邮件。

## 台架问题与实车问题区分

- **判定**：按票据标题（Jira summary / 飞书工作项名称）中的「台架」「实车」标志区分；两者都出现时取最先出现的；都没有时为“未标注场景”。
- **分析**：工作流完全相同；Step 5（及无附件摘要、兜底摘要）提示词注入 `<问题场景>`，按场景给出结论口径：
  - 台架：台架环境，请测试确认是否模拟信号上报。
  - 实车：实车环境，vehicle 通路正常，请按需求确认原因并转对应模块分析。
- **标注**：最终结论开头自动加 `【台架问题】` / `【实车问题】`（随结论回填 Jira / 飞书；已带则不重复；缺附件/拒绝等固定回复不加）；Jira、飞书看板行与详情标题显示「台架」（琥珀色）/「实车」（蓝色）徽标；数据标注工作台显示场景、可按「台架 / 实车 / 未标注场景」筛选，JSONL 导出带 `scene` 字段。
- **召回**：分析 few-shot、历史错误模式、AI 复核纠错样本都只在同规则组**同场景**的历史样本中召回（场景由样本标题判定）；当前票未标注场景时不限场景（保持原行为）。服务端对客户端传入的 few-shot 再按场景兜底过滤。

## 结构化驳回原因与按原因的 few-shot

- 人工驳回（Jira / 飞书）必须选择一个原因类型：信号漏提、时序误判、结论过度、缺日志、模块转错、其他；“其他”必须补充说明，其余补充说明可选；正确结论仍必填。
- 类型存入结果、复核样本与历史（`errorCategory`），`errorReason` 保存为 `【类型】补充说明`。历史无类型的样本按关键词推断，推断不出视为“其他”，不改写原数据。
- 分析时 few-shot 检索：同一错误类型最多取 2 条以保证多样；该票上次被驳回的类型优先；规则组内高频类型有小幅加权。纠错案例以“错误结论（负例，不要重复）→ 人工正确结论”成对给出，并附该类型的复核要点。
- 同规则组（≥3 条同车型纠错时按车型）历史驳回类型的 Top3 以 `<历史错误模式>` 注入提示词作自查提醒；样本少于 3 条或仅“其他”时不注入。

## 数据标注工作台（/labeling）

- 目的：对 MySQL 镜像中的 AI 结论（Jira + 飞书）做人工重新标注，产出更干净的 few-shot 与评测数据；不修改原始分析数据，标注另存。
- 标注项：① 结论判定（完全正确/部分正确/错误/无法标注）；② 错误类型（沿用驳回原因六类，可多选，部分正确/错误必选）；③ 数据用途（正例 few-shot、负例 few-shot、评测真值、排除）；④ 正确结论；⑤ 难度；备注。
- 约束：正例要求完全正确；负例要求错误/部分正确且填正确结论；错误样本作评测真值必须填正确结论；“排除”不能与其他用途同选；“其他”必须写备注。
- 辅助：按已有人工复核/AI 复核/文本特征给“预填建议”和核对提示（仅建议，需人工确认）。
- 权限：登录即可查看；保存/撤销需复核员及以上；标注按登录用户隔离，保留版本号与标注人。
- 导出：`/api/labeling/export` 输出 JSONL（不含排除/无法标注）。尚未自动回灌 few-shot/评测集，需手工或脚本合并。

## 本年度票据统计

首页「本年度统计」支持选择年份和起止月份（默认当年全年至今，如 7–9 月），默认只读当前浏览器 IndexedDB 保留的 Jira 和飞书结果及历史，不修改复核行为。弹窗可切换到「团队（服务器）」，读取 MySQL 镜像中所有成员已备份的记录，展示团队合计与成员明细（见下文）。

- 范围为浏览器本地时区的当年 1 月 1 日至统计时刻，使用结果创建时间或历史原结果时间，不使用归档时间。
- 按来源及结果 ID 去重，当前结果优先；按票据取年度最后一次成功分析，同时间以结果 ID 稳定排序。重跑增加分析次数，不增加票数。
- Jira 按 issueKey 去重；飞书按项目、工作项类型和 ID 去重，缺少快照及分配时回退 assignmentId。
- 展示总票数、成功分析次数和分来源复核通过、驳回、未复核、无法确认数及比率、覆盖率。
- Jira reviewStatus 混有 AI 判断，仅展示「复核通过率（含 AI）」。飞书仅对有 manualReviewedAt 的非 pending 结果计算「人工复核准确率」，旧记录无法确认时不进入分母。
- 比率 = 通过 /（通过 + 驳回）；覆盖率 =（通过 + 驳回）/ 处理票数。无复核数据时比率显示「暂无数据」，两来源不合并准确率。
- 流转时间：统计弹窗按来源及合计展示最大 / 最小 / 平均流转时间，取每张票范围内最后一次分析的 `dwellMs`；缺失（历史记录、找不到接手时间等）按默认 4 小时填充，**流转时间恰为 4 小时的票（含默认填充）不计入平均流转时间**（最大 / 最小仍包含）；团队合计按参与平均的票数加权；范围内无票或全部被跳过时平均显示「暂无数据」。
- 无效身份或时间记录排除并提示；读取失败可重试。不包含失败尝试、已清除数据；「我的」模式不含其他浏览器记录。
- **BoschVehicleHalHash 日志行**：提取 Android 日志时，在所有解压文件（排除压缩包与 CAN trace）中搜索包含 `BoschVehicleHalHash` 的行，去重后（最多 20 行，不受时间窗限制）放在 Android 日志筛选结果最前面，一并进入 Android/QNX 分析输入与证据包；没有信号 ID 时也会保留。
- **Token 统计**：每次分析（`/api/issues/process`，含图片识别，不含 AI 复核）累计 Qwen 返回的 `usage.total_tokens`（缺失时按字符估算），写入该票处理结果的 `tokenUsage`（IndexedDB，随镜像备份到 MySQL）；Jira 详情头部与飞书结果页副标题展示。统计弹窗按来源及合计展示「最大 Token」「每张票平均 Token」，取每张票范围内最后一次分析；无 token 记录的票（历史、旧数据）不计入。支持年份 + 月份区间；团队合计按有记录票数加权。
- **接手时段统计**：按处理结果的 `handoverAt`（经办人改为 `STATISTICS_SOLVE_TIME_USERS` 目标人员的时间，东八区）分为「工作时间」（周一至周五 9:00–19:00）与「非工作时间」（其余时间及周六周日），统计弹窗展示两类转入票数（每票取范围内最后一次分析；范围按分析时间，同月份区间）。无接手时间的票两类均不计入。
- **团队统计**：登录用户可在弹窗切换「团队（服务器）」，由 `GET /api/statistics/team` 汇总服务器镜像（`idb_records`）中所有账号的结果、历史、快照与分配。每个账号按上述规则独立统计，团队合计为各账号之和（同一张票被多人处理时分别计入各自名下），比率与覆盖率按合计重算，流转时间按处理票数加权平均。只返回聚合数字，不含票据内容；未配置 `MYSQL_URL` 或服务器不可用时提示错误。尚未备份到服务器的本地数据不计入。

# 1. 产品定义
## 产品名称

Jira 智能票据分析系统

## 产品简介

本项目是一套面向博世（Bosch）汽车软件团队的 AI 驱动缺陷分析平台。
系统通过自动化流水线，将 Jira 或飞书项目缺陷票（含 CANtrace 附件）的人工分析过程转化为"AI 分析 + 人工复核"模式，显著降低重复性分析工作量，并通过持续学习机制不断提升 AI 准确率。


## 目标用户

本项目面向正在VehicleService VehicleHal中间件开发小团队。

## 业务背景

博世汽车软件团队承接多家整车厂（OEM）的车载软件项目，包括奇瑞（Chery）、吉利（Geely）等。整车厂通过 Jira 提交软件缺陷票，每张票通常附带 CANtrace（.zip 压缩包）和截图（.png）作为问题现场证据。

**当前痛点：**

- 分析人员需手动下载附件、解包、使用专用工具解析 CAN 信号，流程繁琐；
- 每张票分析耗时较长，积压严重；
- 分析结论质量依赖个人经验，标准不统一；
- 已完成的分析结论缺乏沉淀和复用机制。

**目标收益：**

- 通过 AI 自动完成信号提取、日志摘要与一致性分析，将单票分析时间从小时级压缩至分钟级；
- 通过人工复核闭环和 Few-shot 记忆机制，持续提升 AI 分析准确率；
- 标准化分析结论格式，自动写回 Jira，减少人工录入。


## 2. 目标用户与角色

### 2.1 角色定义

| 角色 | 描述 | 主要操作 |
|---|---|---|
| **普通分析员** | 日常查看分析进度和结果，手动触发任务 | 查看规则组列表、查看单票分析详情、手动触发筛票/处理 |
| **人工复核员** | 对 AI 输出的分析结论进行人工标注，保障结论质量 | 标注结论正确/错误、填写正确结论及原因、触发 Jira 回填 |
| **系统管理员** | 负责系统配置和运维，管理规则组及自动化策略 | 配置/修改规则组、控制自动周期开关和间隔、查看系统运行状态 |

### 2.2 使用场景

- **分析员**：每日上班后打开首页，查看各规则组最新筛票和处理进度；对感兴趣的票点入详情页，查看 AI 分析结论。
- **飞书项目分析员**：在主页统一规则组看板中查看和处理飞书项目工作项；`/meegle` 仅保留到主页的兼容跳转。分配与处理状态保存到 IndexedDB，刷新后继续保留。
- **飞书项目筛票**：规则组在主页同时执行 JQL 与 `RuleGroup.meegleMql`。完整 MQL 直接从 `FROM` 数据源解析飞书项目 key，不依赖当前用户是否还有“我的待办”；MQL 匹配发生歧义时，按 `sortOrder`、再按规则组 `id` 确定唯一归属。成功 MQL 是展示和处理范围的唯一依据：无论分配来源或回填状态，未命中项均解除规则组归属；某来源筛选失败时保留另一来源的快照、任务和数据，但失败来源不得回退展示自身的历史成功快照。
- **复核员**：进入详情页后，逐条复核 AI 结论，通过/驳回，驳回时填写正确结论，系统自动保存为学习记忆；对校验结果进行人工改判。
- **管理员**：在首页控制各规则组的自动周期运行；根据项目变化更新规则组的 JQL、CAN 配置和 AI Prompt。

### 2.3 UI 设计原则

前端界面采用数据密集型仪表盘设计，使用中性 slate 与绿色主操作色，支持亮色和暗色主题，详见 `design-system/ivacp/MASTER.md`。

- 规则组以卡片展示，兼顾查询摘要、车型信息和配置操作。
- JQL、MQL 和配置路径使用等宽字体；状态与来源同时提供文字说明。
- 操作支持键盘访问，管理按钮按角色显示。
- 窄屏卡片采用单列，桌面采用多列；不强制其他业务视图使用卡片。
- 飞书工单详情的「基本信息」使用单个外层卡片，属性和经办人在卡片内按单列键值列表展示，不为每个字段重复绘制卡片。

## 3. 核心功能需求

### 3.1 规则组管理（RuleGroup / MAP_CAR_ROLE）

#### 3.1.1 功能描述

规则组是系统的核心配置单元，每个规则组对应一个整车厂/车型/项目的分析场景。系统通过规则组隔离不同项目的分析策略。

#### 3.1.2 规则组属性

| 属性 | 说明 | 是否必填 |
|---|---|---|
| 规则组 ID | 唯一标识符 | 是 |
| 名称 | 规则组显示名称 | 是 |
| JQL 查询语句 | 用于从 Jira 拉取目标票的 JQL | 是 |
| CAN 信号配置文件路径 | 指定解析 CANtrace 所用的信号定义文件 | 是 |
| AI Prompt | 用于 AI 分析的提示词模板 | 是 |
| 自动周期间隔（分钟） | 自动运行筛票+处理的时间间隔 | 否（默认关闭） |

#### 3.1.3 业务规则

- 同一规则组的 JQL 查询结果构成该规则组的"候选票池"；
- 规则组 Prompt 支持变量插值（如 `{issue_key}`、`{can_signals}`）；
- 规则组配置变更后，对已处理票不产生追溯影响。
- 前端规则组仍以 IndexedDB 作为本地工作数据；后端提供 `/api/rule-groups`、`/api/rule-groups/:id` 和 `/api/rule-groups/reorder` 作为管理员规则组管理接口，使用项目本地 `data/rule-groups.json` 轻量持久化，不引入后端数据库。
- 规则组新建、编辑、删除、导入、拖拽排序和 AutoCycle 配置仅系统管理员可操作；普通分析员可查看规则组并执行筛票 / 处理。
- **Bosch Jira 规则组**：首页工具栏提供「新建 Bosch Jira 规则组」按钮。该规则组带 `jiraProvider: "bosch"`，只配置 Bosch Jira JQL（不含飞书 MQL），CAN 配置路径、车型文件和 Prompt 与普通规则组一致，由管理员填写或通过导入文件上传。筛票、处理、回填评论和经办人指派均访问 `BOSCH_JIRA_URL`，使用 `BOSCH_JIRA_USERNAME` + `bosch_jira_api_token` 认证；处理管线与普通 Jira 规则组完全一致，规则组行显示「Bosch Jira」标签。`BOSCH_JIRA_PASSWORD` 仅在缺少 Token 时兜底（Atlassian Cloud 实测登录密码会返回 401）。

### 3.2 筛票任务（FilterTask）

#### 3.2.1 功能描述

筛票任务按规则组的 JQL 查询语句，从 Jira 批量拉取符合条件的缺陷票，生成筛票快照（FilteredIssueSnapshot）。

#### 3.2.2 任务状态流转

```
PENDING → RUNNING → SUCCESS
                  ↘ FAILED
         (超时)→ EXPIRED
```

#### 3.2.3 功能点

- **手动触发**：用户在首页点击"一键筛选"按钮，为指定规则组创建一个筛票任务；
- **自动触发**：AutoCycle 模式下，系统按配置间隔自动创建筛票任务；
- **跨来源自动处理**：主页 AutoCycle 仅依据当次统一筛选返回的来源汇总触发处理：Jira 只处理当次最新成功快照；当次飞书筛选成功时，处理该规则组当前全部 `pending` / `failed` 分配（含既有人工分配），当次飞书筛选失败则不派发飞书处理。Jira 成功而飞书筛选失败时只处理 Jira，不能以历史飞书成功结果替代当次失败结果；
- **指定单票分析**：用户可在操作栏输入指定 Jira 票号（如 CHER-129770）后直接执行。系统检索该票并在标题 `[]`/`【】` 中解析车型标识，去匹配匹配成功的规则组进行单票处理。
- **筛票快照**：每次筛票成功后，将拉取到的 Jira Issue Key 列表持久化为快照（FilteredIssueSnapshot），供后续处理任务使用；
- **增量更新**：同一规则组的多次筛票结果自动去重，避免重复处理；
- **任务超时**：运行时间超过系统阈值的任务自动标记为 EXPIRED。

### 3.3 票据处理任务（IssueProcessTask）

#### 3.3.1 功能描述

对筛票快照中的每张 Jira 票，执行完整的自动化分析流水线，最终生成 AI 分析结论（IssueProcessResult）。

#### 3.3.2 处理阶段（7个）

| 阶段 | 阶段标识 | 说明 |
|---|---|---|
| 准备 | `PREPARING` | 校验票据信息，准备工作目录 |
| 下载附件 | `DOWNLOADING` | 从 Jira 下载 CANtrace ZIP 包、分卷压缩包以及最新 2 张非当前用户上传的图片附件（通过多模态大模型转文本插入上下文） |
| 解包 | `UNPACKING` | 解压 ZIP，获取 `.blf` / `.asc` 等 CAN 日志文件 |
| 解析信号 | `PARSING` | 按规则组 CAN 配置文件解析 CAN 信号，提取关键信号值，输出信号值持续区间摘要，并生成 prop/id 对应关系与时间窗日志摘录 |
| AI 推理 | `MODEL_INFERENCE` | 调用大语言模型（含图像模型）分析信号数据与截图 |
| 生成回复 | `GENERATING_REPLY` | 基于 AI 推理结果，格式化生成 Jira 评论文本。若结果中存在信号或报文不存在的情况，需追加从下载解压文件的最大 cycle 目录的 Buildinfo.txt 中提取的博世 MAIN_VERSION 版本号及描述。 |
| 保存结果 | `SAVING_RESULT` | 服务端完成成功响应；浏览器收到响应后独立持久化结果到 IndexedDB，服务端 `after` 独立异步归档当前运行日志到 Docupedia |

#### 3.3.3 功能点

- **手动触发**：用户在首页点击"一键处理"，仅处理该规则组最新一次成功筛票生成的快照；若尚未筛票或最新筛票结果为 0 票，则按钮禁用；
- **单票触发**：在规则组详情页可对单张票手动触发处理；
- **重复分析**：同一 Jira 票允许再次分析；每次分析都会生成新的 IssueProcessResult，复核状态从 `PENDING` 开始，Jira 回填状态从未回填开始；
- **分析历史**：若该票已有历史分析结果，再次分析前将旧分析结论、人工复核结果和 Jira 回填状态记录为分析历史，供详情页追溯；
- **CAN trace 提取结果输出**：解析 CAN trace 后需输出可读摘要，例如 `CouplingFaultStatus_253h = 0，持续 1189 帧（07:58:30.000 ~ 07:58:55.280）`；
- **CAN 信号交互图**：详情页交互式时序图需按多个信号纵向堆叠展示，所有信号共享同一个绝对时间横坐标（`YYYY-MM-DD HH:mm:ss.SSS`），各信号保留独立纵坐标，图形形态使用纯散点图，不绘制折线或阶梯连接线，便于在同一时间点对比不同信号当前值；CANtrace 回放与图表绘制只允许使用 Step 2 提取并成功匹配到的信号，每个匹配只取一个代表信号，候选池、标题、描述、评论、OCR、few-shot 或配置来源中的其他信号只允许存入 `signals.json` 供审计，不得进入回放，也不得绘图；前端 Chart.js 交互图和锁定视口截图只消费后端返回的提取后 `traceData`，不得读取候选池或审计文件补充系列；用户锁定当前浏览器视口为回填图时，系统需将前端合成图片覆盖服务端 `log/.../can_signals.png`，保存横坐标、纵坐标、图例、信号名称、时间和值等完整图表细节，并以该文件作为后续 Jira 回填附件；
- **配置映射落盘**：Step 2 提取出的信号 token 需在对应车型 `config_车型.json` 中进行归一化匹配，允许命中 `prop`、`getSignals`、`setSignals`，并将命中的配置项落盘到 `signals.json`；
- **信号识别补救**：Step 2 精确匹配未命中的 token 会先做受限模糊 / 别名补救，再通过一次候选内自检尝试匹配真实 `prop`；候选池只保留 Step 2 / Jira 文本 / few-shot 中显式出现且形态像信号的 token（包括 `AVHSts` 这类 PascalCase），最多 40 个，配置文件仅作为匹配目标和同名候选来源标注，不允许把车型配置全集扩入问题候选；补救命中与仍未命中的 token 分别写入 `signals.json.recovered` 和 `signals.json.unmatched`，禁止把候选外的 AI 编造信号带入后续链路；
- **prop id 映射落盘**：所有命中的配置项统一收敛到 `prop` 后，再通过对应 `.proto` 的 `Property_ID` 枚举解析十进制 / 十六进制 id，落盘到 `signals_id.json`；
- **时间窗日志摘录**：需优先从上层评论中提取问题发生起始时间；若评论中存在完整时间戳，则以评论时间范围为准，否则回退到评论中的时间点并默认扩展短时间窗。系统再根据 `signals_id.json` 中的十进制 / 十六进制 id，从解压日志中提取对应日志行，输出到 `extract.md`；
- **CAN trace 格式支持**：`.asc` 通过 `ASCReader` + 手工 CANFD fallback 解析，`.blf` 通过 `python-can` 的 `BLFReader` 解析；两种格式都输出同一类信号持续区间摘要；
- **一致性分析输入**：一致性分析必须基于 CAN trace 提取后结果进行判断，同时可参考原始 CAN trace 片段和上层日志；
- **并发控制**：同一规则组下的处理任务支持并发执行，默认并发数可配置；
- **断点续传**：任务因异常中断后，可从失败阶段重新执行；
- **度量基线**：每次处理需在服务端 `log/<规则组>/<车型>/<IssueKey>/pipeline-metrics.json` 写入机器可读度量，包含阶段耗时、Prompt 输入输出长度、证据完整性和最终状态，用于后续准确率与速度优化；
- **Docupedia 归档**：Jira 与飞书项目在服务端成功响应完成、`ENABLE_DOCUPEDIA=1` 后，通过 Next.js `after` 异步归档当前 run 的 `logRoot`；浏览器收到成功响应后独立持久化 IndexedDB，两者互不作为门槛。归档不参与分析结果、复核或回填判定。系统在目标父页面下创建 `meegle_<随机数>` 根页面，并按 Step 归并本次运行文本日志；`ENABLE_DOCUPEDIA=0` 时关闭自动上传。所有上传文章标题都加同一个 `meegle_<随机数>_` 前缀；同一目录内 `stepN_` 开头且数字相同的文本日志会拼接为一个 `meegle_<随机数>_stepN` 文章，`input_comments.txt` 和二进制产物不上传。不会扫描历史 `log/`、补传旧日志或在进程重启后恢复未完成上传；瞬时网络错误会重试，单个文章最终失败继续其余文章，最终失败仅记录日志；
- **黄金样本基线**：系统提供 `npm run baseline:golden`，从历史 `pipeline-metrics.json` 聚合生成 `docs/golden-baseline/golden-baseline.json` 和 `golden-baseline.md`，作为分析准确率与处理速度的回归基线；
- **Docupedia 月度上传统计**：从本功能启用后，成功创建或确认已存在且正文 `text.length > 500` 的实际归档文章，按服务器本地月份追加到 `log/docupedia-upload-stats/YYYY-MM.jsonl`。合并后的 Step 文章只计一篇；根页面、目录页面、最终失败文章和恰好 500 字符的文章不计入。同月按唯一标题去重，每条记录包含 UTC 上传时间、本地月份、标题、字符数、`created` / `existing` 动作和当月累计篇数。文件保留跨重启和跨月历史，不被 `cleanup:data` 清理；统计写入失败仅告警，不改变归档或分析成功状态，不推算启用前的历史上传数。
- **离线准确率评测**：系统提供 `npm run eval:accuracy` 回放 `log/` 产物；在线自检与离线评测统一使用 `evidence_packet`、`can_signal_summary`、`can_trace_extracted_result`、`signals_id`、`extract` 五类具名可信证据源计算证据接地率 EGR，并在 `docs/golden-baseline/eval-set.json` 有人工稀疏真值时计算信号召回率和结论关键判断命中率；
- **Phase 2 错误归因与证据包**：处理流水线在 Step 5 前生成 `evidence-packet.json`，统一记录匹配 prop、Property ID、信号区间、日志命中、缺失证据和风险标记；离线评测报告按 `signal_missing`、`time_window_mismatch`、`log_evidence_missing`、`ungrounded_conclusion`、`rag_mismatch`、`low_confidence_evidence` 聚合错误原因；
- **Phase 3 评测可信度与证据判定增强**：系统会生成 `eval-set-coverage.{json,md}`，报告人工真值数量、车型覆盖和覆盖比例；Evidence Packet 会按真实时间窗 overlap 计算评论与 trace 是否重叠；EGR 判定会归一化时间、键值断言、标识符和 Property ID，减少格式差异导致的误判；缺失、读取失败或格式错误的证据源进入审计，无法形成有效 EGR 的票标记为 `unknown_missing_evidence` 并从 EGR 均值排除；Step 5 会在结构化证据包生成后对 few-shot 案例做证据精召回 / 重排，实现二段式 RAG 的评测集覆盖闭环；证据校准、自批判与回滚保护均保持 advisory / non-blocking，不阻断处理成功和 Jira 回填流程；
- **图片附件 OCR 识别**：系统自动下载该 Jira 中最新上传的 2 张且非当前用户（`process.env.JIRA_USERNAME`）上传的图片附件。调用多模态模型 `IMAGE_MODEL`（默认 `Qwen3-VL-8B`）将其内容识别提取为文本，并直接追加到评论上下文（`commentsText`）中，以便后续所有 AI 分析阶段使用；
- **飞书项目附件插件与评论附件**：Meegle 适配器会读取评论 Markdown、`file_url` 和 `file_urls` 中的附件，再通过附件插件服务按 `project_key + work_item_type_key + work_item_id` 读取文件列表。由于评论接口只返回不透明 URL，系统会在当前 run 的私有目录预取评论附件并以 CLI 下载结果补齐真实文件名、类型和大小；评论附件使用评论创建时间，与插件附件的 `uploadedAt` 合并进入同一时间筛选。`.asc` / `.blf` / `.zip` / `.7z` 等文件继续复用 Jira 的分类、缓存下载、解压和分析流程，选中的评论附件直接复用预取文件。插件服务不可用时记录告警并继续分析可用评论附件；两类来源均没有 CAN trace 或日志压缩包时，直接返回固定的复测与附件补充结论，不调用仅评论 AI 分析。附件插件服务地址可通过 `MEEGLE_ATTACHMENT_PLUGIN_API_URL` 覆盖。
- **飞书项目结果生命周期**：飞书工作项使用独立的 snapshot、task、result、history 和 validation 表持久化完整分析结果，不复用或修改 Jira 表。首页启动时会检查仍为“分析中”的持久化任务；若其同一不可变 runId 已存在完整的 success 产物，系统自动恢复结果并改为已完成；无完整成功产物但创建未满 2 小时的任务保持原状态，超过 2 小时的陈旧任务收敛为失败并允许重试。完成卡可进入 `/meegle/issues/{workItemId}/result`，查看工单内容、处理阶段、分析结论、CAN 图、白名单运行产物、历史版本和原始快照；结果页可修改当前票经办人，也可确认重新分析，旧结果保留为历史版本，失败时继续保留旧结果。
- **飞书项目人工复核与回填**：AI 复核仅提供建议，不能解除回填门槛。只有人工通过，或人工驳回且填写正确结论后，才允许显式授权回填。用户可编辑评论、选择是否附带 CAN 图，并可选一个状态流转；系统先提交带结果隐藏标记的幂等评论，再执行状态流转，分别保存评论和流转状态，流转失败不会重复评论。
- **飞书原票链接**：飞书结果详情页头部提供「原票地址」，新标签页打开 `https://project.feishu.cn/<空间 simple_name>/<工作项类型>/detail/<工作项 ID>`；simple_name 取自 `.env` 的 `NEXT_PUBLIC_MEEGLE_PROJECT_SIMPLE_NAME`（未配置时回退使用 project_key），修改后需重启前端。
- **经办人接手/转出/停留时间**：Jira 与飞书项目处理结果各增加四个字段。**接手时间**：处理该票（一键处理）时读取工单变更记录（飞书 `workitem list-op-records` 的经办人角色变更，Jira changelog 的 assignee 变更），取经办人**最近一次**被改为目标经办人的时间（目标姓名取自 `.env` 的 `STATISTICS_SOLVE_TIME_USERS`，如 `[HUANG Hongwei, DAI Yungui]`）；该票没有此类记录则四个字段均留空。**转出时间**：处理完成时先按处理结束时间 + 1 小时写入，评论回填成功后改为评论回填成功时间（`commentedAt`）+ 1 小时。**停留时间** = 转出时间 − 接手时间；找不到接手时间时接手时间留空，停留时间默认记 4 小时。**是否周末**：停留时间超过 24 小时且接手当天（东八区）为周六或周日时为“是”，其余为“否”。读取变更记录失败不影响分析结果。当前仅在飞书项目结果详情页「飞书项目回填」面板展示，Jira 侧只保存数据。
- **飞书项目经办人流转**：标准工单详情和分析结果页均可按姓名、邮箱或用户 ID 模糊搜索当前项目全部成员，并在二次确认后独立替换“经办人”角色。操作使用详情凭据、目标绑定授权和二次读取冲突校验；经办人已变化时要求刷新重试，且不触发状态流转、评论、复核或重新分析。
- **飞书项目 MQL 筛票一致性**：规则组展示和处理范围以成功 MQL 查询结果为唯一依据；完整 MQL 的 `FROM \`project_key\`.\`work_item_type\`` 同时提供查询所需项目 key，不再先读取“我的待办”。同一工作项命中多个规则组时，使用 `sortOrder` 和 `id` 稳定决策。飞书返回 `data: {}`、`list: null` 时代表 MQL 成功但命中 0 条，系统必须完成本地对账；成功查询会解除该规则组内所有未再次命中的分配（包括已完成、已回填和人工分配）的规则组归属，但不会删除分析结果或历史。单规则组筛选还依赖其高优先级比较 MQL；任一所需查询失败时仅写入审计并保留原有归属，不影响 Jira 链路。界面以最新一次筛选任务为当前结果边界：最新任务失败时显示失败状态和空的当前票列表，不得回退展示更早的成功快照。
- **多模型支持**：
  - 文本分析：Qwen3-32B-FP16（内网私有部署）
  - 图像分析：Qwen3-VL-8B（处理 PNG 截图）

### 3.4 AI 复核（Review）

#### 3.4.1 功能描述

在 AI 生成分析结论后，系统可调用 AI 进行 Few-shot 复核，判断结论是否符合质量标准。复核入口在单票详情页展示，点击后调用验证模型执行二次审核。

#### 3.4.2 复核状态

| 状态 | 说明 |
|---|---|
| `PENDING` | 尚未复核 |
| `PASS` | AI 复核通过，结论合格 |
| `FAIL` | AI 复核未通过，需人工介入 |

#### 3.4.3 业务规则

- 复核使用 Few-shot 方式，将历史 IssueReviewSample（错例样本）注入 Prompt，提高复核准确性；
- AI 复核使用 `.env` 中的 `VALIDATE_QWEN_MODEL` 和 `VALIDATE_API_KEY`，与主分析模型配置解耦；
- 复核 Prompt 需包含完整分析上下文：Jira 描述、评论、原始快照、CAN 信号摘要，以及服务端分析日志中 Step1-5、信号映射、日志筛选和最终回复文本；
- 复核 FAIL 的结论不自动写回 Jira，需人工复核后决策；
- AI 复核只更新建议状态，不写入学习样本；只有人工通过或人工驳回才更新 `IssueReviewSample`。
- **prop/signal RAG**：历史纠错案例召回除 Jira 标题外，还会使用 `prop`、signal token、Property ID、车型等 evidence fingerprint；Embedding 服务不可用时仍回退标题 Token 重叠度。

### 3.5 人工复核（Manual Review）

#### 3.5.1 功能描述

人工复核员在前端对 AI 生成的分析结论进行人工标注，是结论质量的最终把关环节。

#### 3.5.2 功能点

- **结论查看**：在单票详情页完整展示 AI 分析结论（含信号数据、AI 推理过程、最终结论）；
- **标注操作**：
  - **通过（PASS）**：确认 AI 结论正确，结论可进入 Jira 回填流程；
  - **人工改判（FAIL）**：标记 AI 结论错误或修正既有复核结论，填写：
    - 失败理由（必填）
    - 正确结论（必填）
- **统一复核样本**：人工驳回保存 `correction` 样本，人工通过保存 `approved` 样本；同一 `ruleGroupId + issueKey` 始终只保留当前复核对应的一条记录，复核结果切换时覆盖旧样本并清除旧 Embedding 缓存；
- **真实证据指纹**：处理响应将当前 run 的车型、已匹配 `prop`、signal token 和十进制/十六进制 Property ID 保存为 `reviewEvidence`，Jira 与飞书项目在人工复核时使用同一结构写入样本；旧结果缺少该字段时只从标题、结论和信号摘要保守提取明确 token；
- **学习记忆与召回**：后续 AI 分析通过 Embedding 语义检索同规则组复核样本，失败时回退标题 Token 相似度；混合排序同时考虑车型和结构化证据重合，正样本至少满足车型相同或一个结构化证据精确重合才可进入 Step 5；
- **Few-shot 职责隔离**：Step 5 将纠错样本与人工确认样本分别放入“历史纠错案例”和“历史正确案例”；正确案例只参考分析结构和决策模式，任何历史事实都不能覆盖当前票 Evidence Packet、CAN 摘要或日志摘录；
- **修改复核**：人工复核后允许在限定时间内修改标注结果。

### 3.6 AI 校验（Validation）

#### 3.6.1 功能描述

对 AI 分析结论与 CANtrace 实际解析信号进行一致性校验，为人工复核提供客观依据，并生成系统判定结果。

#### 3.6.2 校验运行（IssueValidationRun）

每次 AI 校验生成一条 IssueValidationRun 记录，包含：

- 校验时间
- 系统判定（`system_verdict`）
- 人工改判（`manual_verdict`，初始为空）
- 关联的校验子项列表

#### 3.6.3 系统判定值

| 判定 | 含义 |
|---|---|
| `PASS` | AI 结论与 CAN 信号数据高度一致 |
| `FAIL` | AI 结论与 CAN 信号数据存在明显冲突 |
| `WARNING` | 存在不确定项，建议人工复核 |
| `UNKNOWN` | 无法判定（数据不足或解析失败） |

#### 3.6.4 校验子项（IssueValidationCheck）

每条 IssueValidationRun 包含若干 IssueValidationCheck，每个子项对应一个具体校验点（如某路 CAN 信号的期望值 vs 实际值）。

#### 3.6.5 功能点

- **校验触发**：处理任务完成后自动触发，也支持手动重新触发；
- **结构化证据校验**：处理完成后，系统从 AI 结论中抽取信号值、时间窗、复现判断等结构化断言，并与 CAN trace 摘要、`signals_id.json`、`extract.md` 和上层日志摘录逐项比对，生成 `IssueValidationCheck`；
- **Step 5 证据自批判与多轮自愈**：最终结论落盘前会复用证据接地率判定，对未接地断言触发多轮自愈性修订（最多 3 轮），通过接地率回滚保护（Rollback Guard）选取最佳版本，并写入 `evidence-grounding.json`（含完整调试历史）与 `pipeline-metrics.json.groundingBefore/groundingAfter`；
- **辅助性质**：结构化证据校验、EGR 校准和来源审计均为 advisory / non-blocking；`FAIL` / `WARNING` 用于提示人工复核证据冲突或证据不足，不阻断处理成功或 Jira 回填，Jira 回填仍以人工复核 `PASS` 为前置条件；
- **详情查看**：在校验详情页（`/group/:id/processed/:issueKey/validation/:validationRunId`）展示所有校验子项的详细比对结果；
- **历史校验**：支持查看同一票据的多次历史校验记录。

### 3.7 人工改判（Override）

#### 3.7.1 功能描述

人工复核员可对 AI 校验的系统判定（`system_verdict`）进行人工改判，将最终有效判定写入 `manual_verdict`。

#### 3.7.2 功能点

- **改判操作**：在校验详情页，人工可将系统判定改为 `PASS`/`FAIL`/`WARNING`/`UNKNOWN` 中的任意值；
- **改判记录**：改判时间、改判人、改判原因均需记录；
- **优先级**：存在 `manual_verdict` 时，以 `manual_verdict` 为最终有效判定；
- **权限控制**：仅人工复核员及以上角色可执行改判操作。

### 3.8 Jira 回填（Comment）

#### 3.8.1 功能描述

将通过人工复核的分析结论，经人工确认后写回到对应 Jira 票的评论区。

#### 3.8.2 功能点

- **触发条件**：人工复核标注为 PASS 后，或人工改判为 FAIL（已拒绝）且填写了人工正确结论后，用户可在详情页手动触发回填；
- **评论格式**：按预设模板格式化输出，包含分析摘要、信号数据表格、结论等；
- **幂等保护**：同一票据同一版本结论不重复回填；
- **回填状态**：记录回填成功/失败状态，失败时支持手动重试；
- **预览与编辑**：回填前支持预览最终评论内容，并允许人工编辑评论正文；实际提交到 Jira 的内容以编辑后的正文为准。

### 3.9 Jira 状态流转（Transition / Assignee）

#### 3.9.1 功能描述

用户可在单票详情页手动指派新经办人。为了契合实际工作流，流转指派时不需要修改 Jira 票的状态，而仅修改 Jira 票的经办人。

#### 3.9.2 功能点

- **相关人员候选**：打开指派经办人弹窗时，从 Jira 票详情中过滤相关人员候选，包括经办人、报告人、创建人、评论作者、关注人和其他用户型字段；
- **更新经办人**：用户选择目标人选后，系统调用 Jira assignee API 指派经办人，跳过 transition 状态流转；
- **状态刷新**：指派成功后，单票详情页立即刷新本地快照中的经办人显示；
- **错误反馈**：Jira 返回 400/权限错误/网络超时时，弹窗展示中文错误信息，允许用户修改后重试。

#### 3.9.3 业务规则

- 指派人候选使用 Jira 返回的用户名作为提交值，显示名仅用于前端展示；
- 必须选择明确的经办人后才允许保存；
- 修改经办人与系统内部 `reviewStatus`、`validationStatus`、`hasCommentedToJira` 相互独立，不做自动联动；
- 指派经办人失败不得修改 IndexedDB 中的票据状态。

### 3.10 飞书通知

#### 3.10.1 功能描述

在关键业务事件发生时，通过飞书 Webhook 向配置的群组推送通知。

#### 3.10.2 通知触发时机

| 事件 | 通知内容 |
|---|---|
| 单票处理成功 | Jira 或飞书项目工单主题、描述、处理结果、结果图片链接（如有）、处理时间 |
| 单票处理失败 | Jira 或飞书项目工单主题、描述、失败原因、处理时间 |

#### 3.10.3 业务规则

- 通知失败不影响主业务流程；
- 通知内容不包含敏感数据（如 Jira 账号密码）。
- 若处理结果存在图片，当前版本在 webhook-only 模式下通过卡片链接跳转图片地址，不直接上传本地图片到飞书。
- 飞书项目票的处理通知（成功/失败）在卡片最后附加该票在飞书项目中的原票链接（与结果页「原票地址」一致）。

### 3.11 自动周期运行（AutoCycle）

#### 3.11.1 功能描述

系统支持对每个规则组独立配置自动周期运行，到达周期时自动依次执行"筛票 → 处理"完整流程。

#### 3.11.2 数据模型（AutoCycleState）

| 字段 | 说明 |
|---|---|
| 规则组 ID | 关联规则组 |
| 是否启用 | 开关状态 |
| 周期间隔（分钟） | 每次自动运行的时间间隔 |
| 上次运行时间 | 最近一次自动触发时间 |
| 下次运行时间 | 预计下次触发时间 |
| 当前运行状态 | 由前端调度器运行锁派生，防止同一规则组重叠触发 |

#### 3.11.3 功能点

- **首页控制**：在首页规则组卡片上直接开关 AutoCycle，并调整周期间隔；
- **状态展示**：首页显示各规则组 AutoCycle 的开关状态、周期间隔和下次运行时间；
- **防重叠**：当前周期任务未完成时，跳过本次触发，等待下一个周期；
- **故障恢复**：AutoCycle 状态持久化到 IndexedDB，页面重新打开后恢复本地调度。
- **来源隔离**：每轮以当次统一筛选的来源汇总决定处理范围；一方筛选失败不阻断另一方成功来源的处理，也不读取失败来源的历史成功快照或分配。

### 3.12 远程终端（Remote Shell）

第一版提供 `/terminal` 内网页面，只允许连接服务端环境变量配置的白名单服务器。用户可多标签打开实时 SSH 终端；关闭标签或页面即断开 SSH。命令输入会写入审计日志，命令输出不落盘。页面访问受本地登录态保护，账号来源为 `docs/login.json`；远程访问时，浏览器默认连接当前页面所在服务器的 Terminal Gateway 端口，也可通过 `NEXT_PUBLIC_REMOTE_SHELL_GATEWAY_URL` 覆盖。服务端白名单目标支持私钥、私钥 passphrase、密码或 ssh-agent socket 认证，敏感字段只保存在服务端环境变量中。

终端支持复制粘贴：选中文字后 Ctrl+C（有选区时复制，无选区仍发送中断）、Ctrl+Shift+C 复制；Ctrl+V / Ctrl+Shift+V / Cmd+V 粘贴；右键有选区则复制、否则粘贴。读取剪贴板需浏览器授权且需安全上下文（localhost 或 HTTPS），否则粘贴退回浏览器原生行为（Shift+Insert）；多行粘贴仍按命令护栏逐条检查。

远程终端支持从 `docs/project.json` 读取项目选择配置。用户连接服务器后，可在左侧选择 `projectName` 和分支；选择项目会在远程 shell 中自动执行 `cd mainPath`，例如 `chery-8255` 会切换到 `~/workspace`；选择分支会对该分支配置的每个 repo 执行 `git checkout branchName`。若 checkout 因未提交文件失败，则自动执行 `git stash push -u` 压栈后重试 checkout。页面右侧展示当前分支下每个 repo 的 `git status --short --branch`，输出按 git status 行类型着色，并且右侧分栏支持拖拽调整宽度。每次终端命令提交后，系统会自动刷新该状态；也可手动点击刷新。在 Repo 状态分栏中，对于未通过 `git add` 暂存的文件（包括修改未暂存文件及未跟踪文件）以及已暂存的文件（包括已修改暂存、新增暂存和删除暂存文件），其前方都会提供复选框供多选。每个 repo 卡片底部提供 `git add` 按钮、`checkout` 按钮和 `git reset` 按钮，点击即可对勾选的文件远程执行 `git add`（暂存）、`git checkout`（撤销工作区修改，需用户确认）或 `git reset`（撤销暂存区修改）操作，命令执行完成后自动清空勾选状态并刷新 git 状态。终端还会按当前项目分支下每个 repo 的 `repoPath/tools/json/config_*.json` 自动生成配置复选框，复选框名称取自 `config_*.json` 中的 `*`；配置复选框绑定当前 `repoPath + branchName`，路径或分支任意一个变化时都会清空旧列表并重新扫描。默认全选表示保留，用户取消勾选后点击“配置”，系统会对所有未选中的配置文件远程执行受限的 `git checkout -- tools/json/config_*.json`，并刷新配置列表和 git 状态。页面提供上传 xls、上传 dbc、上传 mcu.h 三个入口，分别写入 `mainPath/scriptPath/`、`mainPath/repoPath/tools/sdb/`、`mainPath/repoPath/tools/inc/`。一键 checkout 会对当前分支下所有 repo 执行 `git checkout .`；一键 pull 会对所有 repo 执行 `git pull`。配信号按钮会在远程 shell 中切换到 `mainPath/scriptPath`。打包按钮会在 `mainPath/scriptPath` 中打包 `types.hal`、`VHAL_SIGNAL_CHECKLIST_s.xls`、`com.bosch.cm.platform.vehicle.proto` 和 `CHERY_8255_VHAL_SIGNAL_V数字.数字.数字.xls` 匹配文件为 zip，并下载到本地。检验checklist按钮会通过 base64 形式，直接下载 `mainPath/scriptPath` 下的 `VHAL_SIGNAL_CHECKLIST_s.xls` 文件到本地。

## 4. 非功能性需求

### 4.1 性能需求

| 指标 | 要求 |
|---|---|
| 筛票响应时间 | 单次 JQL 查询（≤100 票）完成时间 ≤ 30 秒 |
| 单票处理时间 | 全流程（含 AI 推理）≤ 10 分钟/票 |
| 前端页面加载 | 首屏加载时间 ≤ 3 秒（内网环境） |
| 并发处理能力 | 同一规则组支持至少 5 张票并发处理 |
| API 响应时间 | 普通查询接口 P95 ≤ 500ms |

### 4.2 可靠性需求

- **任务持久化**：所有任务状态持久化至数据库，服务重启后任务状态不丢失；
- **断点续传**：处理任务在失败阶段可重新执行，不重复已完成阶段；
- **幂等保护**：同一票据的 Jira 回填操作保证幂等，不产生重复评论；
- **故障隔离**：单张票处理失败不影响同批次其他票的处理；
- **服务可用性**：系统 SLA ≥ 99%（内网部署环境）。

### 4.3 安全需求

- **认证鉴权**：
  - 所有 API 接口需携带有效 Token；
  - 前端路由按角色权限控制访问（`/geely2` 等需登录）；
  - Token 过期后自动跳转登录页；
  - 未携带有效 Token 的业务 API 返回 401；角色不足的 API 请求返回 403；
- **数据安全**：
  - Jira 账号凭证、AI 模型 API Key 等敏感配置通过环境变量或加密配置文件管理，禁止硬编码；
  - 飞书 Webhook URL 按规则组隔离，不对外暴露；
  - CANtrace 附件文件仅存储于服务器本地，不对外公开访问；
- **操作权限**：
  - 人工复核（驳回/通过）仅限复核员及以上角色；
  - 规则组配置修改仅限系统管理员；
  - AutoCycle 控制仅限分析员及以上角色。
  - 规则组后端写接口（创建、更新、删除、排序）仅限系统管理员，未登录返回 401，角色不足返回 403。

### 4.4 可用性与可维护性

- **日志**：所有处理任务的每个阶段记录结构化日志，包含任务 ID、票据 Key、阶段名称、耗时、错误堆栈；
- **度量**：所有处理任务输出 `pipeline-metrics.json`，记录 `PREPARING`、`DOWNLOADING`、`UNPACKING`、`PARSING`、`AI_STEP1`~`AI_STEP5` 等阶段耗时，以及 CAN/DBC/信号/日志证据完整性；
- **错误提示**：前端对所有接口错误给出友好的中文提示，不暴露技术细节；
- **配置化**：AI 模型地址、并发数、超时阈值、飞书 URL 等均通过配置文件管理，无需修改代码；
- **数据库迁移**：使用 mysql 管理数据模型变更，支持版本回滚；
- **API 文档**：后端提供 OpenAPI JSON（`/api/openapi`）和 Swagger UI（`/api/docs`），覆盖当前已实现的 Next.js API Routes，方便前后端联调。

### 4.5 兼容性

- **浏览器**：支持 Chrome 90+、Edge 90+（内网环境主流浏览器）；
- **Python 版本**：Python 3.10+；
- **Node.js 版本**：Node.js 18+（前端构建）；
- **操作系统**：Linux（Ubuntu 20.04+）服务端部署。

## 5. 业务约束与限制

### 5.1 外部依赖约束

| 依赖系统 | 约束说明 |
|---|---|
| Jira | 使用 Jira REST API v2/v3；账号须具备目标项目的读权限和评论写权限 |
| AI 模型服务 | Qwen3-32B-FP16 和 Qwen3-VL-8B 为内网私有部署，不可访问外网模型；模型服务不可用时，处理任务进入 FAILED 状态 |
| 飞书 | 飞书 Webhook 需提前在群组中创建并配置；飞书不可用时，主业务流程不受影响 |
| CAN 信号配置文件 | 需与规则组绑定的实际车型 DBC/Excel 文件保持同步更新；文件变更后需重新处理已有票据 |

### 5.2 数据约束

- **附件大小**：单张票的 CANtrace ZIP 包大小限制为 500MB，超限时跳过下载并记录警告；
- **历史数据**：AnalysisTask 和 IssueAnalysisResult 为历史兼容模型，新功能不再写入这两个模型，仅保留只读查询能力；
- **数据保留**：处理结果、附件文件默认保留 90 天，过期后自动清理（可配置）；
- **FastSnapshot 去重**：同一规则组同一 Issue Key 在有效期内不重复创建处理任务（需同一筛票快照未过期）。

### 5.3 业务流程约束

- 筛票任务必须先成功完成，才能触发对应规则组的处理任务；
- 人工复核（PASS）是触发 Jira 回填的唯一前置条件，AI 复核 PASS 不自动触发回填；
- AutoCycle 的最小周期间隔为 5 分钟，防止频繁请求 Jira API；
- 同一张 Jira 票在同一规则组下，同时只允许一个处理任务在运行（防止并发冲突）。

### 5.4 AI 模型约束

- 模型输入 Token 限制：单次推理上下文 ≤ 32K tokens，超限时自动截断 CAN 信号数据；
- 图像输入限制：单次图像推理最多 4 张 PNG，分辨率超过 4096×4096 时自动缩放；
- 模型输出为非结构化文本，系统通过正则/结构化提取解析结论，解析失败时任务标记为 FAILED。

## 本地数据要求

项目数据保存在浏览器本地 IndexedDB 中，IndexedDB 是主存储。

刷新页面后，项目数据应该继续存在。

本项目必要时可使用 SQLite 或 MySQL 数据库。当前使用本地 Docker 中已启动的 MySQL（`mysql-9.3.0`，库 `jira_analyzer_next`）作为服务端镜像，连接串由 `.env` 的 `MYSQL_URL` 配置；未配置时系统照常运行，仅提供文件备份。

## 数据备份与服务器镜像

背景：统计、知识库、复核样本原先只存在一个浏览器里，换电脑或清缓存就会丢失，团队成员（如 HUANG Hongwei、DAI Yungui）的数据也无法汇总；人工复核样本又是提升解票准确率的评测真值和 RAG 燃料。

- 首页操作条「数据备份」弹窗，覆盖 IndexedDB 全部表（处理结果、复核样本、分析历史、校验、知识库、对话、记忆、笔记、规则组等）。
- **文件备份**：一键导出整库 JSON（保留 Date 类型）；导入时默认只补齐本地缺失的记录，可勾选覆盖本地同 id 记录。
- **服务器镜像（MySQL）**：
  - 自动增量同步：登录后，本地每次新增、修改、删除记录约 3 秒后推送到服务器；失败时 60 秒后重试，待推送队列保存在 localStorage，刷新后继续。
  - 首次在某浏览器启用时，后台自动执行一次完整备份，把已有本地数据补齐到服务器。
  - 「完整备份到服务器」：上传全部本地记录，并把本浏览器此前上传、本地已不存在的记录标记删除；不会删除同账号其他浏览器上传的数据。
  - 「从服务器恢复」：把当前账号在服务器上的数据恢复到本浏览器（默认只补齐缺失记录），恢复写入不会再次回推。
- 服务器数据按登录账号（session `username`）隔离；弹窗展示服务器记录数、最近同步/完整备份时间、同步异常，以及团队成员各自的记录数，为后续团队汇总统计打基础。
- 删除在服务器上为软删除；IndexedDB 仍是主存储，服务器不可用时不影响任何分析、复核和回填流程。

## 团队模板并发一致性（2026-10-28）
