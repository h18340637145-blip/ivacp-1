# 处理页面闪烁与证据判定校准设计

## 1. 背景

当前项目在开始处理 Jira 票据后，首页、规则组分析列表和单票详情页都会出现频繁刷新闪烁。同时，最新离线评测覆盖 67 张票（跳过 4 张），平均 EGR 为 57.5%，信号召回率为 83.3%，结论关键判断命中率为 33.3%。46 张票被归类为 `ungrounded_conclusion`，热点集中在时间戳、`getMsgId/getSignals` 和 `keycode` 等断言。

本轮包含两个按顺序实施、独立验收的目标：

1. 收窄处理状态订阅，消除处理期间的页面闪烁。
2. 校准在线与离线证据判定，减少确定性的证据误报。

## 2. 目标与非目标

### 2.1 目标

- 处理任务状态变化只重新渲染依赖该状态的组件。
- 保留现有加载提示、按钮状态、并发策略和页面布局。
- 在线 `computeGrounding()` 与离线 `eval:accuracy` 复用同一证据归一化规则。
- 正确识别时间戳、键值断言、prop/signal 和 Property ID 的等价表达。
- 未接地断言提供可审计的未命中原因和已检查证据源。
- 使用当前评测中的典型问题构建回归样本，并重新生成离线评测报告。

### 2.2 非目标

- 不新增页面、处理遮罩或进度展示方式。
- 不改变 IndexedDB 数据结构、处理并发数或 API 合约。
- 不引入新模型、新数据库或平行分析流水线。
- 不扩大可信证据范围到模型生成内容。
- 不把证据校验改为 Jira 回填的硬阻断条件。
- 本轮不实施结构化断言生成，也不扩充人工真值集。

## 3. 页面闪烁修复

### 3.1 根因边界

`KanbanBoard`、`AnalysisBoard` 和 `IssueDetail` 当前通过无选择器的 `useProcessTaskStore()` 订阅整个 Zustand Store。批量处理时，每张票开始、完成以及相关状态写入都会通知这些页面，造成与当前视图无关的重复渲染。并发处理会放大该现象。

### 3.2 设计

- `KanbanBoard` 仅选择 `runAll` 和 `runOne`。
- `AnalysisBoard` 仅选择任务列表展示所需的 `tasksBySnapshot`、`resultsBySnapshot`、`runningIds` 及操作函数。
- `IssueDetail` 仅选择当前详情页需要的状态集合及操作函数。
- 选择器使用稳定、可复用的写法；不得退回无选择器订阅。
- 不修改现有组件层级、加载占位符、动画样式或处理状态文案。

### 3.3 状态与数据流

1. 用户从任一入口发起处理。
2. `runOne` 将当前 snapshot 加入 `runningIds` 并写入任务状态。
3. 只有读取相关字段的页面或组件响应状态更新。
4. 处理完成后，当前 snapshot 的任务和结果更新，其他页面结构保持稳定。
5. IndexedDB 写入和刷新后恢复逻辑保持不变。

### 3.4 回归保护

新增静态回归检查，覆盖三个入口组件：

- 禁止直接调用无参数 `useProcessTaskStore()`。
- 确认各组件仍能取得其使用的操作函数和状态字段。
- 保留现有处理、前端和构建检查。

## 4. 证据判定校准

### 4.1 统一归一化边界

在 `lib/analysis` 内形成单一证据归一化能力，由在线结构化证据校验与离线评测共同调用。归一化只改变比较形式，不改变原始证据内容。

支持以下等价表达：

- 时间：完整日期时间与 `HH:mm:ss.SSS`、毫秒位数差异、同一时间的重复引用。
- 键值：`key=value`、`key 为 value`、空值表达、大小写和空白差异。
- 数值：语义一致的十进制与十六进制 Property ID。
- 标识符：prop、signal、`getMsgId`、`getSignals` 的大小写和常见包装文本差异。

### 4.2 可信证据源

判定继续只消费现有可信产物：

- `can_signal_summary`
- CAN trace 提取结果
- `signals_id.json`
- `extract.md`

模型回复、few-shot 文本和候选池不能作为断言自证来源。

### 4.3 判定结果与审计

每条断言的判定结果至少包含：

- 原始断言与归一化形式
- 是否接地
- 命中的证据源和证据摘要
- 未命中时已检查的证据源
- 未命中原因，例如格式不支持、证据源缺失或内容不一致

现有 EGR 与错误分类字段保持兼容。新增审计信息采用可选字段，旧产物仍可回放。

### 4.4 错误处理

- 单一证据文件缺失时记录缺失来源，继续检查其他可信来源。
- 无法解析的断言保持未接地，不使用模糊猜测强制命中。
- 归一化异常不得中断主处理流程，回退到当前保守判定。
- Step 5 自批判与 Rollback Guard 保持辅助模式；校验结果不阻断 Jira 回填。

## 5. 测试与验收

### 5.1 页面闪烁

- 新增 Store 订阅静态检查并先验证旧实现会失败。
- 三个处理入口均不得无选择器订阅整个 Process Store。
- 现有处理状态、完成结果和 IndexedDB 持久化检查通过。
- Next.js 构建通过。

### 5.2 证据校准

为以下断言建立固定回归用例：

- 时间戳的完整日期、纯时间和毫秒精度差异。
- `getMsgId=null` 与 `getMsgId 为 null`。
- `getSignals=ADS_5_ELKSettingSt` 的等价表达。
- `keycode=535` 的日志证据命中。
- 十进制与十六进制 Property ID 等价。
- 内容真实不一致时仍必须判为未接地。

执行现有 Phase 1、Phase 2、Phase 3、RAG 和结构化证据回归检查。重新运行 `eval:accuracy`，对比修复前后的：

- 平均 EGR
- `ungrounded_conclusion` 数量
- 时间戳、键值断言误报数量
- 仍然缺失的真实信号和日志证据数量

指标提升只代表证据判定改善，不直接声明端到端业务准确率提升。

## 6. 实施顺序

1. 为无选择器 Store 订阅增加失败回归检查。
2. 收窄三个页面的 Store 订阅并验证页面行为。
3. 为证据归一化热点增加失败回归用例。
4. 实现共享归一化与审计信息。
5. 对齐在线校验和离线评测调用路径。
6. 运行全套相关回归、构建和离线评测。
7. 同步产品文档、架构文档和 `session-handoff.md` 中受影响的行为说明。
