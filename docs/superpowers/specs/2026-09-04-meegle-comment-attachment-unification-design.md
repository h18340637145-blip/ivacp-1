# 飞书评论附件统一处理设计

## 目标

飞书问题票分析同时检查评论附件和附件插件附件。评论附件使用评论创建时间，插件附件使用 `uploadedAt`；两类附件补齐真实文件名后合并为同一候选池，继续复用现有附件分类、时间比较、下载、解压和分析流程。

## 数据流

1. `/api/meegle/context` 和兼容的 `/api/meegle/analyze` 读取完整评论。
2. 从评论 Markdown、`file_url`、`file_urls` 提取仅限 `project.feishu.cn` 的安全附件引用，并继承所属评论的 `created_at`。
3. 飞书接口无法在下载前返回评论附件的原始文件名，且对象存储拒绝 `HEAD` 与 Range GET。因此在当前 run 的私有暂存目录预取全部评论附件，通过 `attachment +download` 的结果补齐原始文件名、MIME 和大小；单个附件预取失败时记录告警并继续其他候选。
4. 将已补齐的评论附件与附件插件附件按 URL 去重合并。插件附件继续使用 `uploadedAt`，评论附件继续使用评论时间。
5. 共享处理流水线继续按现有规则选择最新 `.asc` / `.blf` 与最新日志压缩包。选中的评论附件复用暂存文件，选中的插件附件按原逻辑下载；未选中的评论暂存文件在分类完成后删除。分卷包仍按原逻辑补齐兄弟分卷。

## 结果规则

- 评论附件比插件同类附件新时，选择并下载评论附件。
- 插件附件更新时，仍选择插件附件。
- 最新 CAN 与最新日志包的 90 分钟、2 小时时间判断保持不变。
- 合并候选池不存在 CAN trace 或日志压缩包时，不再调用仅评论 AI 分析，直接返回：`车控车设问题分析需要CAN trace，请复测并提取问题发生时的Android log, QNX log, CAN trace，依次从应用->Framework再转给VHAL分析，谢谢`
- Jira 附件行为保持不变；固定结论仅适用于飞书项目来源。

## 安全与失败处理

- 评论附件仍只接受无凭据的 `https://project.feishu.cn` URL。
- 下载签名和真实下载 URL 不落日志、不返回浏览器。
- 评论附件预取使用 run 级私有暂存目录和安全文件名；分类完成后删除未选文件，处理结束后清理暂存目录。
- 不向飞书项目执行评论、流转或字段写入。

## 测试

- 评论附件预取补齐真实 `.asc` / `.tgz` 文件名并保留评论时间，选中文件可复用且未选文件会清理。
- 评论与插件存在同类文件时，现有分类选择时间较新的来源。
- 两类来源都没有 CAN/日志时，飞书来源返回固定结论且不进入 AI 评论分析。
- Jira 的无附件行为保持原样。
- 既有评论附件、插件附件和飞书结果生命周期测试继续通过。
