# 飞书项目 Jira 同构筛票设计

## 背景与目标

`/meegle` 使用飞书项目（Meegle）当前用户的 `mywork todo` 作为工单来源，但首页展示、筛选和处理操作需与 Jira 首页保持一致。飞书待办不使用 JQL；系统从每张待办的名称、类型和缺陷描述中抽取车型、项目和平台，并自动分配到已有规则组。

本设计只改变飞书项目的展示和筛票链路，不改变 Jira 的数据、JQL、筛票快照或处理链路。

## 已确认的业务规则

- 首页采用 Jira 规则组行布局与操作语义，不保留飞书专用泳道作为主界面。
- “一键筛选”扫描当前用户的全部飞书待办，将可匹配且未被人工分配的工单写入对应规则组。
- 每个规则组的“筛选票”同样扫描全部待办，但只写入属于当前规则组的工单。
- 模型不能可靠匹配规则组的工单保留在“待分配”列表。
- 人工拖拽分配拥有最高优先级；后续一键筛选或规则组筛选都不得修改、移除或覆盖该分配。
- 每次分配、未分配、跳过和异常均保留可追溯日志。

## 前端设计

`/meegle` 复用 Jira 首页的规则组总览、状态、筛选票、一键筛选和一键处理的视觉层次与交互语义。规则组行显示飞书来源的待办数量、最近筛选时间和筛选状态；规则组详情展示当前组已归属工单及相关筛选审计记录。

“待分配”区域显示模型未匹配工单和人工取消分配的工单。手工拖拽仍可把工单分配到任一规则组，并在审计日志中标记为人工操作。

## 筛选和分类数据流

1. 服务端筛选编排接口从 `mywork todo` 自第 1 页开始连续翻页，直到返回空页或不足一页，取得全量待办。
2. 对每张待办获取或补齐必要字段，至少包括项目身份、工作项 ID、名称、类型和缺陷描述。
3. 尚未人工分配的工单按受控批次输入 `Qwen3-32B-FP16`；模型仅负责输出 JSON 中的 `carModel`、`project`、`platform` 和置信/缺失信息。
4. 服务端用确定性规则匹配已有规则组：车型配置精确或归一化命中优先，其次规则组名车型命中，最后项目与平台联合命中。单独项目或平台不足以自动分配。
5. 接口按触发范围返回候选结果。一键筛选返回所有匹配结果；规则组筛选只返回目标规则组的匹配结果。两种入口共享同一分类和匹配实现。
6. 前端将可自动分配结果保存到飞书专用 IndexedDB assignment 表；未匹配项不创建规则组分配，继续显示在待分配区域。

## 手工分配保护

assignment 必须持久化 `assignmentSource`，取值为 `manual` 或 `auto`。筛选运行遇到 `manual` assignment 时，记录 `skipped_manual_assignment` 审计事件并保留原规则组。自动分配结果可以在后续筛选中刷新到新规则组，除非被用户手工分配或取消分配。

## 审计日志

新增飞书专用 IndexedDB 筛选审计记录，至少保存：

- `id`、`runId`、`createdAt`、触发类型（全量或规则组）和目标规则组；
- 工作项三元身份（project key、type key、work item ID）及展示名称；
- 模型名称、车型、项目、平台、模型解析状态和必要时的错误摘要；
- 决策（`assigned`、`unassigned`、`skipped_manual_assignment`、`failed`）；
- 目标规则组、匹配评分/依据或未匹配原因。

前端日志视图按最近筛选运行和当前规则组过滤，便于追溯“哪个 issue 被分配到哪个规则组，为什么”。日志不保存模型密钥、完整提示词或敏感认证信息。

## 接口与错误处理

筛选编排只在服务端调用 Meegle CLI 和 Qwen。接口显式选择 `Qwen3-32B-FP16`，低温度调用，并对模型 JSON 做校验；单个批次模型失败时，为该批次工单生成 `failed` 审计记录，不影响其他批次。待办列表、工作项详情或模型调用失败时返回可读错误和已完成统计，前端不覆盖既有 assignment。

模型输出为空、JSON 无法解析、字段不足或确定性匹配未达到门槛时，均按未匹配处理，工单留在待分配列表。
