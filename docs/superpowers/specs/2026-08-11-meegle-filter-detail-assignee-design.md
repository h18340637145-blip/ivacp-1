# 飞书项目筛选结果、完整详情与经办人变更设计

## 背景

当前飞书项目规则组筛选已使用独立的 Meegle MQL，并通过 `MeegleAssignment` 保存自动或人工分配以及后续分析状态。不过，规则组卡片的飞书票数依赖内存中的来源摘要：刷新后不能恢复最近一次成功筛选状态，并且 0 票时徽标会被隐藏。筛选结果列表又直接读取 assignment，导致最新 MQL 命中集合与历史处理记录、人工分配记录混在同一个数据口径中。

飞书工单详情当前只请求 `description,priority`，评论仅在分析上下文中获取，普通详情页无法展示完整基本信息、全部描述和评论。现有页面支持状态流转，但不能搜索飞书项目成员或修改“经办人”。

## 目标

1. 每个配置了飞书 MQL 的规则组卡片常驻显示最近一次成功筛选的“飞书 0/N 票”，刷新后不丢失，并可点击查看该次筛选集合。
2. 每张筛选出的飞书票都能在尚未分析时打开详情；详情展示当前基本信息、完整描述、明确的缺陷描述以及全部评论/备注。
3. 保持现有状态流转行为不变，新增独立的经办人变更操作。人员候选来自当前飞书项目的全部团队，支持输入部分姓名搜索完整名称。
4. 保留现有 MQL 唯一归属、人工分配保护、分析结果和审计历史。

## 非目标

- 不改变 Jira 的 JQL、筛选、详情或经办人逻辑。
- 不恢复历史的 Qwen 飞书待办分类接口。
- 不将飞书详情或成员目录保存到后端数据库。
- 不把经办人变更与状态流转绑定为一个操作。
- 不引入登录、云同步或新的协作能力。

## 已确认的产品决策

- 卡片票数表示最近一次成功 MQL 筛选的原始命中集合，不表示全部历史 assignment。
- 成功筛选为 0 时必须持久化，并显示“飞书 0 票”。
- 点击 0 票也进入筛选结果页，页面展示明确空状态。
- 经办人变更是独立操作，默认不修改；确认后只修改飞书“基本信息 -> 经办人”，不改变工单状态。
- 页面采用 Jira 同构的信息层级和操作语义，但飞书数据读取与写入仍由独立适配器完成。

## 总体架构

```text
Meegle MQL
  -> MeegleFilterTask
  -> MeegleFilteredIssueSnapshot
       -> 规则组卡片最近成功票数
       -> 当前筛选结果列表
       -> 当前工单详情入口

MeegleAssignment
  -> 唯一归属与人工分配保护
  -> AI 处理状态与结果
  -> 历史、复核和审计

Meegle live detail API
  -> 全字段工作项 + 全部评论 + 作者名称
  -> 当前详情页

Meegle assignee APIs
  -> 跨团队人员模糊搜索
  -> 授权绑定的经办人角色替换
```

筛选快照与 assignment 是两个明确边界：前者回答“最近一次 MQL 查到了什么”，后者回答“该票如何归属、处理并保留历史”。二者通过工作项身份 `projectKey + workItemTypeKey + workItemId` 关联，不互相替代。

## IndexedDB 数据模型

数据库升级一个版本，新增两张表。

### MeegleFilterTask

- `id`: 筛选任务 ID；可复用服务端 `runId` 加规则组 ID 组成稳定标识。
- `runId`: 同一次全量或单规则组筛选的运行 ID。
- `ruleGroupId`: 规则组 ID。
- `projectKey`: 飞书项目空间 key。
- `mql`: 本次执行的 MQL 快照。
- `status`: `running | completed | failed`。
- `issueCount`: 成功时的原始命中数量，允许为 0。
- `createdAt`、`completedAt`、`error`。

索引至少覆盖 `id, ruleGroupId, status, createdAt`。

### MeegleFilteredIssueSnapshot

- `id`: `taskId + workItemIdentity` 的稳定标识。
- `filterTaskId`、`ruleGroupId`。
- `projectKey`、`projectName`。
- `workItemTypeKey`、`workItemId`、`workItemName`、`stateName`。
- `rawData`: MQL 返回且经安全归一化的筛选字段。
- `createdAt`。

索引至少覆盖 `id, filterTaskId, ruleGroupId, workItemId`。

### 持久化语义

- 每次筛选开始即创建 `running` 任务。
- 服务端成功返回后，在同一 IndexedDB 事务内写入快照并把任务置为 `completed`；0 票时写入空快照集合，仍完成任务。
- 服务端失败时把当前任务置为 `failed`，不删除最近一次成功任务及其快照。
- 卡片和列表统一选择该规则组最新的 `completed` 任务。
- 历史任务可保留用于追踪；本需求不新增历史筛选 UI。

## MQL 筛选接口与状态流

`/api/meegle/filter` 保持现有校验、MQL 查询、优先级裁决和 assignment 审计能力，同时增加按规则组返回的归一化原始命中集合。返回结果不能只给总数，因为客户端必须用同一批数据持久化列表快照。

原始命中集合在唯一归属裁决前形成，因此：

- 卡片数量与 MQL 实际返回一致。
- 人工分配或高优先级裁决不改变“该 MQL 命中过这张票”的事实。
- 分析入口仍根据工作项身份关联 assignment；没有 assignment 或分析结果也可以查看当前详情。

`RuleGroupWorkflowStore` 负责创建和完成飞书筛选任务。页面启动时从 IndexedDB 加载最近成功任务，而不是从全部 assignment 反推票数。Jira `FilterTask` 逻辑保持不变。

## 规则组卡片和筛选结果页

### 卡片

- 配置了非空 `meegleMql` 时始终渲染飞书票数徽标。
- 未执行过成功筛选时显示 0；执行中可同时展示运行状态，但不能抹掉上次成功票数。
- 成功筛选后显示最新 `issueCount`，包括 0。
- 筛选失败时显示失败提示，并保留上次成功的票数入口。
- 徽标统一链接到 `/analysis/{ruleGroupId}/meegle`。

### 列表

- 读取最近成功 `MeegleFilterTask` 对应的快照，而不是直接读取 `MeegleAssignment`。
- 0 票时展示中文空状态，并保留返回、刷新和重新筛选路径。
- 每行按工作项身份关联 assignment，展示已有 AI 状态；无 assignment 时显示“未处理”，但工单 ID 仍可点击。
- 工单 ID 链接到 `/meegle/issues/{workItemId}`，通过查询参数携带 `projectKey`、`workItemTypeKey` 和必要的规则组上下文。
- 已有 `/meegle/issues/{workItemId}/result` 路由继续保留，作为分析结果详情入口。

## 当前飞书工单详情

新增以工作项身份为输入的可复用详情数据适配器和标准详情页面。详情页面不依赖分析 snapshot 或 result，因此未分析工单也能打开。

### 读取接口

工作项详情读取使用 `workitem get --fields ["_all"] --auto-paginate`，避免当前只读取 `description,priority`。评论使用 `comment list --auto-paginate`。两个请求通过 `Promise.allSettled` 并行执行，使评论失败时仍能返回工作项正文；评论作者 user key 再批量解析为姓名。

接口返回明确的规范化结构：

- `identity`：项目、类型和工作项 ID。
- `attributes`：标题、状态、创建人、更新时间、模板、角色成员等基本信息。
- `fields`：保留 `key, name, value` 的完整字段数组。
- `descriptionFields`：名称或 key 表示描述/缺陷描述/实际结果的字段。
- `comments`：评论 ID、作者 key/姓名、创建时间、正文和附件。
- `assigneeRole`：角色 key、角色名和当前成员。

### 展示规则

- “描述”区域完整保留正文段落和换行，不截断。
- 名称为“缺陷描述”的字段单独突出；若模板将缺陷内容写在通用 `description` 中，则明确突出正文内的“实际结果/缺陷描述”段落，并保留完整原文。
- 其他描述类字段按飞书返回顺序全部展示。
- “基本信息”展示当前状态、优先级、报告人、经办人、创建/更新时间等可读字段。
- 评论/备注按时间顺序展示全部正文、作者和时间。
- Markdown 图片或附件转换成受控预览/下载入口；不通过 `dangerouslySetInnerHTML` 执行飞书返回内容。
- 详情、评论作者解析或附件加载失败时分区显示错误，不让次要区域遮蔽已成功加载的正文。

## 人员模糊搜索

CLI 的 `user search` 只能解析完整姓名、邮箱或 user key；对部分姓名（例如“尧”）不会返回“尧华”。因此人员候选使用项目团队接口：

1. `team list --project-key <projectKey> --auto-paginate` 获取项目全部团队。
2. 对每个团队执行 `team list-members --team-id <teamId> --auto-paginate`。该接口返回成员 user key，不直接返回姓名。
3. 限制并发，等待所有团队查询成功，按 user key 去重并记录所属团队。
4. 将 user key 每 20 个一组交给 `user search`，解析完整姓名和邮箱，构建项目成员目录。
5. 对项目成员目录中的完整姓名和邮箱执行规范化后的部分字符串匹配。

客户端输入防抖，并使用 `AbortController` 取消旧请求。服务端按项目短时缓存完整成员目录；缓存到期后重新获取团队、成员 key 和用户资料。只有所有团队及用户批次均成功时才缓存并返回完整目录；任何团队或用户批次失败都返回明确错误，不把不完整候选伪装成全量搜索结果。

空查询不加载全量成员，要求输入至少一个非空字符，避免无界目录请求。结果数量设置合理上限，但服务端必须先完成跨团队分页和去重，再应用展示上限。

## 独立经办人变更

详情页提供独立的“修改经办人”区域，不与现有状态流转表单合并。默认不选择目标人员，也不会产生写操作。

操作流程：

1. 用户搜索并选择目标人员。
2. 页面展示“当前经办人 -> 目标经办人”。
3. 用户请求写操作授权；新增授权动作类型 `assignee`。
4. 授权声明绑定 `projectKey + workItemId + expectedCurrentUserKeys + targetUserKey`，防止替换目标或旧经办人集合后重放。
5. 提交时服务端重新读取工作项和“经办人”角色；若当前成员集合与 `expectedCurrentUserKeys` 不一致，返回冲突并要求刷新确认。
6. 当前已经是目标人员时返回幂等成功，不调用更新接口。
7. 否则用同一次 `workitem update --role-operate` 请求移除全部当前经办人成员并添加目标 user key。
8. 成功后重新加载详情；失败时保留页面上的当前人员和状态，并显示安全错误摘要。

角色 key 不在客户端硬编码。服务端优先使用当前详情里名称为“经办人”的 `role_members`；必要时通过 `workitem meta-roles --role-query 经办人` 精确确认。该工单当前角色为 `role_b43b38`，但实现必须支持不同项目或模板的角色 key。

现有 `/api/meegle/workflow` 状态流转接口和页面行为保持不变。经办人更新失败或成功都不能自动触发状态流转。

## 授权与安全

- 扩展现有 Meegle 写授权联合类型和签发/校验逻辑，新增 `assignee`。
- 服务端校验项目、工作项、页面所见当前经办人集合、目标用户和授权声明完全一致。
- 客户端只传业务身份和授权令牌，不接触飞书凭据。
- 所有外部字符串按不可信输入渲染；错误响应不返回命令、令牌或内部堆栈。
- 用户搜索只读；只有二次确认后的经办人接口可执行角色更新。

## 错误处理

- 筛选失败：新任务标记失败，保留最近成功票数和列表。
- 筛选成功为 0：保存成功任务和空集合，卡片更新为 0。
- 详情部分失败：按基本信息、描述、评论分区展示已成功数据和错误。
- 人员无结果：显示“未找到匹配人员”，不自动选择近似结果。
- 人员搜索部分失败：整个搜索标记失败，允许重试。
- 经办人已发生外部变化：服务端返回冲突，不覆盖新值；客户端刷新详情后再次确认。
- 经办人更新失败：不修改本地详情缓存，不影响状态流转。

## 测试策略

### 单元和服务端测试

- 最近成功飞书筛选任务选择以及 0 票持久化。
- 当前筛选快照不受历史 completed assignment、人工分配和失败重筛污染。
- MQL 原始命中集合与 assignment 裁决分别持久化。
- `_all` 多页字段合并、完整描述保留、缺陷描述/实际结果识别。
- 评论分页、作者解析和附件归一化。
- 项目团队分页、跨团队部分姓名搜索、去重、结果上限和部分失败。
- 经办人角色动态解析、相同目标幂等、移除旧成员并添加目标成员。
- `assignee` 授权不能修改 project、work item、expected current users 或 target user 后重放。

### UI 和回归测试

- 卡片在未筛选、0 票、N 票、运行中和失败后均有稳定显示。
- 0 票徽标可点击并进入空列表。
- 无分析结果的筛选票可以打开当前详情。
- 完整描述、缺陷描述和评论/备注可见。
- 人员搜索、选择、二次确认、成功刷新和失败重试可用。
- 现有状态流转、Meegle MQL、assignment、分析结果和复核流程继续通过。

验证至少包括相关专项测试、`npx tsc --noEmit`、lint、构建、IndexedDB 刷新持久化检查和浏览器端到端页面检查。所有 Node 命令显式优先使用 `/home/huo2wx/.nvm/versions/node/v20.20.0/bin`。
