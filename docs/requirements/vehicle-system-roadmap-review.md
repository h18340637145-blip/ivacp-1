# 车辆信号分析后续开发方向（审核稿 v0.1）

- 状态：**待审核**，未开始实现；审核通过前不改动任何代码。
- 日期：2026-11-04
- 依据：[docs/vehicle-system/](../vehicle-system/README.md) 六章手册与 validation.md（核对基线 2026-10-15）、现有 [PRODUCT.md](../PRODUCT.md) / [ARCHITECTURE.md](../ARCHITECTURE.md) 中的信号检查、VHAL 版本、RAG few-shot 能力。
- 边界：手册为源码阅读结论，未做编译、实机、台架验证；本稿的方向均需在对应阶段用真实工单/日志验证，不把推断当事实。

## 1. 现状与差距

IVACP 目前已具备：Jira 工单筛选、日志收集与信号筛选、VHAL 版本/配置快照、Excel（Vehicle property ID / MCU UP / IVI DOWN / Project）信号存在性检查、RTC→VS 提交关联、few-shot RAG、AI 复核与回填。

手册揭示的系统事实与当前分析能力之间的差距：

| 编号 | 手册事实 | 当前分析的缺口 |
|---|---|---|
| G1 | 链路分段：MCU→INC→QNX Bus→PropContext→过滤→FDBus→Android HAL→缓存→上层（06 章分段排障） | 证据按"日志命中"组织，没有按链路段标记"数据停在哪一层" |
| G2 | get 有三种读取语义（SDK 缓存 / 服务 GET / 服务缓存），DEFAULT≠真实 0，set 入队≠车端执行 | AI 结论易把"get 返回值"当作实时采样，缺少语义守卫 |
| G3 | discard、`USR_VEHICLE_SIGNAL_FILTER_ENABLED`、`openSignalFilter`、drop timer、CONTINUOUS 重发是不同机制 | 只检查信号是否在表里，不判断"是否被过滤/丢弃导致 Android 侧不更新" |
| G4 | HIDL/AIDL 两条分支行为不同（错误传播、离线缓存、checkHealth） | 分析未区分工单所属 HAL 分支 |
| G5 | 车型矩阵 8 个，T1YA 在 Android loader 显式池中未列出 | 车型匹配只比对 Excel Project 列，不校验两侧 loader/配置一致 |
| G6 | 配置生成脚本有副作用与已知不匹配（旧 parser、`vehicle.sh -a`、ConfigManager 被替换） | 远程终端放权后，缺少对高风险命令的识别提示 |
| G7 | 手册 7 项"待确认项"（lunch 目标、FDBus 跨 OS 配置、T1YA、超时阈值等） | 知识库没有"已确认/待确认"分级，AI 可能把待确认项当结论 |

## 3. 各方向说明

### D1 手册知识化（P0）

- 把 vehicle-system 六章按"链路段 / 机制 / 症状 / 证据来源"拆成结构化条目（如 JSON：id、章节、断言、证据类型 `源码已核实 | 教学简化 | 待实机确认`、适用分支 HIDL/AIDL/共同、适用车型）。
- 7 项待确认项显式标记 `unverified`，AI 引用时必须带"待确认"措辞。
- 接入现有 RAG（知识库/侧栏对话与分析 prompt），复用 few-shot 检索审计，不新增向量服务。
- 验收：条目可追溯到章节与行号；待确认项不会以肯定语气出现在结论中（用固定用例检查）。

### D2 链路分段诊断（P1）

- 定义分段与日志特征：①配置/车型选择 ②MCU/INC 上行 ③QNX Bus 解码与 discard ④PropContext 缓存与过滤 ⑤FDBus 连接/订阅 ⑥Android HAL 缓存与事件 ⑦上层权限/订阅。
- 在 `collectEvidence` 之后新增"分段判定"步骤：对每个待查信号，输出各段"有证据 / 无证据 / 无法判断"，给出"数据最后出现的段"。
- 结论文案与现有转派分类（转对应模块 / 转对手件 / 再转给 VHAL 分析）建立映射表，由用户审核后才改动判定规则。
- 前置：需要用户提供各段的典型日志关键字（手册只给了排障思路，未给出日志格式），先做小样本人工标注。
- 验收：在标注样本上，"停止段"判定与人工一致率达到审核时约定的阈值（建议先定为观察指标，不设硬门槛）。

### D3 语义守卫规则（P1）

- 在分析 prompt 增加手册 G2 的硬约束：不得用 get 返回值证明实时采样；DEFAULT 状态不等于真实零值；set 返回 OK 不等于车端执行；时间戳来源需说明。
- 增加后置校验：结论中出现上述错误推断模式时标记"需人工复核"，而非自动改判。
- 按工单 HAL 分支（HIDL/AIDL，来源于 VHAL 版本/配置）注入对应差异提示（错误传播、AP_POWER_STATE_REPORT 离线缓存、checkHealth）。
- 验收：构造针对每条守卫的负例用例，模型输出被标记或纠正；不降低现有测试断言。

### D4 配置一致性检查扩展（P2）

- 在现有 VHAL/Excel 检查基础上增加：车型是否同时存在于 VS 车型列表与 Android loader 池（T1YA 即典型待确认项）。
- 仅报告"提示"级别，不阻断流程，沿用现有"unknown 继续"的原则。
- 先只读取同步到本地的 type.h / 配置快照，不新增远程写入。
- 验收：对 T1YA 等已知差异车型产出提示且标注"待产品集成确认"。

### D5 终端高风险命令识别（P2）

- 把手册脚本风险表（`vehicle.sh -a/-p/-c`、VS CMake 配置 `REMOVE_RECURSE`、`vs_config_clean`、ConfigManager 替换）转成命令守卫的"警告"规则，在终端执行前提示副作用，不自动拦截（拦截策略需用户另行决定）。
- 验收：触发这些命令时界面出现中文风险提示并写入审计；其他命令行为不变。

### D6 评测与回归集（P3）

- 复用 `eval:export-truth` 的真值导出，补充按链路段/机制分类的样本标签，用于衡量 D2–D4 的收益；不跑真实工单回填。

### D7 手册维护流水线（P3）

- 手册基线 HEAD 哈希与当前工作区比对，源码前进时在界面提示"手册可能过期"；与 D1 条目联动标记受影响条目。

## 4. 建议实施顺序

1. D1（单独一轮，可验收、风险最低）。
2. D3（依赖 D1 的条目，改动集中在 prompt 与后置校验）。
3. D2（需先由你提供日志特征样本，再做小样本标注试点）。
4. D4 / D5 按需插入；D6 在 D2 开始前同步准备数据；D7 最后。

每个方向独立成一轮，遵循"一次一个明确目标"，各自更新 PRODUCT/ARCHITECTURE/WORKFLOW/时序文档与 session-handoff。

## 5. 不在范围内

- 不修改 VehicleService / BoschVehicleHal 源码，不实现手册中提到的生产缺陷修复。
- 不新增云服务、第三方账号体系或真实 GitHub API；存储沿用 IndexedDB + 现有 MySQL 镜像。
- 不做实机/台架验证；mock、离线、真实业务证据在每轮结果中分别说明。
