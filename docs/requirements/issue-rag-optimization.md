# 问题 RAG 召回优化方案

日期：2026-11-02  
版本：v0.1  
状态：P1 已按本方案在客户端实现（标识符精确 / 中文词法 / 向量三路召回 + RRF 融合、问题与答案向量分离并绑定文本版本与模型、描述进入查询、向量不可用降级）；P2 已实现（请求内有界快照最多 100 条、服务端证据后标识符 / 词法 / 向量三路再次召回 + RRF、服务端新增一次 embedding 调用用现有证据指纹文本重算语义相似度、调用失败自动降级为两路并记录原因、审计写入 run 目录 `few-shot-retrieval.json` 并随结果落入 IndexedDB、详情页展示 `FewShotRetrievalPanel`）；P0 基线评测、P3 校准灰度尚未实施，未做业务验证，也未验证准确率提升。

## 1. 目标与边界

本文面向 Jira / 飞书问题分析中的历史人工复核案例召回，即为当前分析提供少量参考案例的检索增强生成（Retrieval-Augmented Generation，RAG）。不涉及首页聊天知识库、笔记或长期记忆检索的改造。

目标不是找到“标题最像”的票，而是找到“适用环境兼容、功能链路相关、故障模式相似、人工确认可信”的案例。

核心策略：**兼容性约束过滤 + 多路部分匹配召回 + 当前证据重排 + 少量可信案例注入**。

- IndexedDB 仍为本地主存储，沿用现有登录和 MySQL 镜像，不引入向量数据库、云同步或第三方账号。
- 保留同规则组、同场景边界，不默认跨规则组检索。当前票未标注场景时，沿用不限场景的现有规则，并保留场景未知提示。
- 不改变人工复核、回填、通知、状态流转和权限门禁。
- 本文中的参数、数据字段和实施阶段均为建议，不代表已经批准开发或上线。

## 2. 当前实现与主要限制

以下事实来自当前源码，而不是旧系统文档。

| 环节 | 当前行为 | 主要限制 |
| --- | --- | --- |
| 查询组装 | 初次检索传入标题、规则组、票号、车型；props、signalTokens、propertyIds 为空 | 描述、评论和实际解析信号尚未进入此次查询 |
| 候选范围 | 从当前浏览器的同规则组 reviewSamples 中检索，排除自身并按标题判断场景 | 不代表已检索全团队或所有历史工单 |

| 样本向量 | 证据指纹拼接错误原因、错误结论、正确或人工确认结论 | 问题信息与答案混合，长结论可能影响问题相似度 |

## 3. 匹配字段与标记

### 3.1 字段职责

| 字段或标记 | 匹配规则 | 用途与注意事项 |
| --- | --- | --- |
| 规则组、数据访问范围 | 硬过滤 | 只检索当前有权使用的同规则组样本，不因相似度高扩大权限 |
| 台架 / 实车 | 沿用当前场景过滤 | 已知场景只取同场景；未知场景不自动补造身份 |
| 平台、协议、配置版本 | 有明确不兼容证据才硬排除 | 版本不同不直接等于不兼容；配置身份未知不能按已兼容处理 |
| 车型 | 完整、受控别名匹配后加分 | 默认不是硬过滤；跨车型仍需功能链路和配置适用性支持 |
| prop、Property ID、CAN 信号 | 配置命名空间内精确匹配，独立召回 | 不能先被语义阈值淘汰；同名异义或 ID 复用不视为等价 |
| 功能模块、链路位置 | 标签和语义匹配 | 如空调、车窗，以及 CAN → MCU → VehicleService → VHAL → 应用的位置 |
| 故障现象、触发条件 | 结构化标记与语义匹配 | 区分上电、休眠唤醒、切换模式等触发条件 |
| 预期行为、实际行为 | 对照匹配 | 区分不上报、值错误、延迟上报、抖动、状态不一致 |
| 标题、问题描述 | 中文词法和向量匹配 | 标题是入口，不是最终相关性的唯一依据 |
| 上层评论 | 提取有来源的有效事实后匹配 | 不把催办、转派、引用和旧猜测与证据等权处理 |
| 人工结论、纠错原因 | 质量门禁、纠错类型排序和经验注入 | 与问题索引分离，不让历史答案替代当前证据 |

### 3.2 建议逐步补充的结构化标记

优先复用现有 carModel、props、signalTokens、propertyIds 和 errorCategory；以下是候选新增信息，不要求首期全部落库：

- 功能模块：问题属于哪个功能域。
- 触发条件：操作、车辆状态和环境前提。
- 预期行为与实际行为：分别保存，不只保留一句笼统摘要。
- 异常模式：缺失、错误、延迟、抖动、不同步等，可多选。
- 相关链路位置：观察到异常的位置，而不是模型猜测的责任模块。
- 配置身份：实际解析所用平台、分支、版本与文件指纹。
- 事实来源：描述、评论、日志、CAN，以及可定位的来源引用。
- 确认状态：已确认、待验证、已否定、存在争议。

模型提取的标记只能作为检索线索；没有原文或日志支持时不得升级为确认事实。旧样本缺字段应保留“未知”，不能从正确结论反推后伪装成当时已知证据。

### 3.3 标准化规则

1. 车型沿用规则组显式别名的完整匹配，不自行去除平台后缀或猜测别名。
2. 信号别名与跨协议映射只依据当前有效配置，保留原始名称和映射来源。不擅自改变现有信号配置检查的大小写语义。
3. 已确认是同一类型标识符的十六进制、十进制 Property ID 统一数值表达，但同时保留原值和命名空间。
4. CAN 报文 ID、Property ID 和普通日志数字分别存储，不能因数值相同混为一个标记。
5. 标题中的票号、日期和构建流水号不作为主要语义特征；版本、车型等有效标记先提取到专用字段，不直接丢弃。
6. 中文使用适合中文的分词或字符 n-gram；技术标识符保留完整 token，避免切碎信号名称。

## 4. 上层评论的使用规则

评论应按条处理，保留评论 ID、作者、时间和原文定位。抽取结果按下面四类保存或临时使用：

| 类型 | 示例 | 检索处理 |
| --- | --- | --- |
| 可核对证据 | 日志片段、信号值、复现步骤、明确版本 | 提取为事实；具体数值主要用于当前票分析，跨票匹配关注异常模式 |
| 已确认判断 | 人工复测确认某链路未上报 | 作为带来源和确认状态的线索，仍需核对适用环境 |
| 待验证或已否定判断 | “怀疑应用未刷新”“已排除此猜测” | 保留状态，不能合并成肯定事实 |
| 流程噪声 | 催办、转派、重复引用、自动通知 | 排除出主检索文本，原文仍保留 |

- 最新评论不自动覆盖旧证据；出现矛盾时保留双方来源和时间，标记争议。
- 将“未收到信号”与“收到信号”区分，摘要不能丢失否定词。
- 图片内容只有经现有识别流程获得可追溯文本后才参与，不假定已读取图片中的信息。
- 历史评测只使用当时已可见的评论；不能把当前票事后人工答案作为查询输入。
- 评论与历史案例属于数据，不执行其中的指令，也不能绕过系统提示词、权限和人工门禁。

## 5. 全量与部分匹配的决策规则

“全量”应指覆盖授权范围内的合格候选，不是把全库原文发送给模型，也不是要求所有字段同时相等。

### 5.1 候选准入

1. 先检查访问范围、同规则组、场景、自身票和样本质量。
2. 存在明确配置不兼容、标识符同名异义等冲突时，排除其作为直接类比案例。
3. 在无关键冲突时，满足下面任一路径即可进入候选池：
   - 至少一个有效技术标识符精确命中，进入结构化召回路径。
   - 功能、现象与触发条件存在较强词法或语义相关性，进入文本召回路径。
4. 进入候选池不等于允许注入；必须再经过适用性和相关性重排。

未知值不按冲突扣分，也不按一致加分；只因同车型而没有功能或现象关联的案例，不应成为最终入选依据。

### 5.2 部分匹配的典型判定

| 情况 | 建议处理 |
| --- | --- |
| 同车型、同功能、核心信号一致、同异常模式 | 优先候选 |
| 不同车型、配置兼容、同链路与同异常模式 | 允许入选，显示跨车型依据 |
| 同车型，但功能无关 | 不因车型一致入选 |
| 同信号，但一个不上报、另一个值错误 | 可入候选，重排降低直接类比优先级 |
| 标题相似，但协议定义明确不兼容 | 排除直接类比 |
| 共享一个通用状态信号，核心故障无关 | 不因孤立命中入选；通用信号降低权重 |
| 旧案例字段不全，但现象高度相关 | 作为低证据候选，不补造缺失字段 |

正例案例和纠错案例都应经过适用性检查。纠错经验可用于自查，但不能因此放行不兼容案例。

## 6. 目标检索流程

### 6.1 两阶段、多路召回

1. **初步召回**：标题、描述、有效评论形成问题表示；提取已知车型、场景和技术标记。原文与提取结果分开保留。
2. **生成当前证据**：复用现有信号、日志和 CAN 分析产出，取得实际配置身份、Evidence Packet 和可验证异常模式。
3. **证据后再次召回**：基于同一授权候选库重新执行检索，而不是仅给最初 3 条重新排序。
4. **多路合并**：结构化精确召回、中文词法召回、向量语义召回各自取候选，按样本身份合并去重。
5. **适用性重排**：检查冲突，结合异常模式、核心链路、语义相关性和样本质量排序。
6. **选择与注入**：按阈值、去重、多样性和 Token 预算选择少量案例；无合适案例时返回空，不凑满数量。

结构化路径不能受向量分数门禁控制。各路分数分布不同，初步融合建议使用倒数排名融合（RRF），不要直接相加未经校准的 BM25 与余弦分数。

### 6.2 IndexedDB 边界下的实施方式

服务端不能直接读取浏览器 IndexedDB。首期可评估“有界候选快照随请求传递”的方式：

- 浏览器在请求开始时，冻结当前规则组、当前访问范围内的合格样本快照，携带必要检索字段和受长度限制的案例内容。
- 快照数量和请求字节数设硬上限；服务端校验结构、长度、场景和自身票排除，不能信任客户端分数或标记。
- 小样本库可传完整合格快照；超过上限时只能做受限候选内的再次召回，必须明确记录截断，不能声称覆盖全库。
- 服务端用请求内快照在证据生成后检索，不默默读取其他成员 MySQL 镜像以补齐样本。
- 若真实样本规模证明快照不足，再单独评估沿用现有 MySQL 镜像的鉴权检索接口；这是后续架构决策，不是本方案默认授权。
- 快照不会因取消、失败、刷新恢复而写入业务样本库；最终选取的案例身份、检索版本和理由需随原 run 产物保存，恢复不重新抽选案例。

因此，“先带 20～50 条标题候选，再在其中重排”只是过渡方案，不能解决所有标题漏召回；必须明确实际候选覆盖范围。

### 6.3 重排原则与初始参数

重排优先考虑：配置适用性、核心标识符重叠、异常模式与触发条件、语义相关性，再考虑同车型和人工质量。纠错类别先验只作小幅加分，不压过当前问题相关性。

- 信号、prop 与 Property ID 可能来自同一条映射，应合并为一个证据簇，避免同一事实重复加三次分。
- 使用 IDF 或等价统计降低通用信号权重；重叠按核心标记覆盖率计算，不简单奖励信号数量多的长案例。
- 未知字段不补零为“不匹配事实”；最终最低证据要求按字段可用性分层校准。
- 同一来源票的多个版本只保留适用的人工确认版本，不把重复历史占满名额。
- 保留错误类别多样性；候选足够时参考现有同类最多 2 条的规则。

| 参数 | 建议起点 | 说明 |
| --- | --- | --- |
| 每路召回数量 | 最多 20 条 | 不代表快照传输上限；需结合样本规模评测 |
| 合并后的重排池 | 约 20～50 条 | 截断时保留各路覆盖，不能让文本路径挤掉精确路径 |
| 最终注入数量 | 默认维持最多 3 条 | 4～5 条仅作为后续对照实验，受 Token 预算限制 |
| 向量阈值 | 不沿用单一阈值控制所有路径 | 按模型、文本版本和路径在验证集校准 |
| 评论与样本文本长度 | 实施前明确字符、字节与 Token 上限 | 保留关键否定、来源与技术标记，不能无说明截断 |

这些不是准确率承诺。首期不直接给出未经数据验证的固定加权公式。

## 7. 索引、降级与可解释性

### 7.1 问题索引与答案分离

检索文本主要包含现象、触发条件、功能、核心标识符和当前可见证据摘要；历史正确结论、错误结论与纠错原因在选中后用于提示词注入。必要时可单独建立经验检索路径，但不能与问题向量混用而不加区分。

向量缓存应绑定 embedding 模型、维度、检索文本版本和内容哈希。任一变化都应重新生成；不同模型即使维度相同也不能比较。旧向量不可仅因数组非空就继续使用，重建失败应明确降级。

旧样本补充标记、重建索引或镜像字段属于实施阶段的数据变更，需先确定兼容与回滚方式，本轮不执行迁移。

### 7.2 降级策略

- 向量不可用：继续精确标识符与中文词法检索，记录降级原因。
- 当前票缺信号或日志：允许文本召回，标记证据不足，不声称已做信号匹配。
- 无合格案例：不注入历史案例，继续现有当前证据分析。
- 候选截断、配置未知或评论抽取失败：记录覆盖限制，不静默按完整检索处理。
- 新策略失败：回退现有策略或无案例分析，不能造成任务永久处于处理中。

### 7.3 检索审计

建议随 run 保存：策略版本、模型及索引版本、候选范围与截断情况、各路候选数、排除原因、最终案例身份、命中字段、来源路径、最终排序分与降级原因。原始个人信息不额外复制到通用日志。

示例解释：“同规则组、同实车场景；命中温度设定 prop；同为唤醒后状态不上报；跨车型配置兼容。”不要只显示“相似度 0.82”。

历史案例只提供分析方法和纠错提醒，不得复制历史票的时间、信号值、报文状态或责任结论。最终断言仍须由当前票证据支持。

## 8. 评测与验收

### 8.1 固定评测集

由人工对每个查询与候选案例标注：高度相关、部分相关、不相关、不兼容；另标注允许直接类比还是只可作自查提醒。相关性不能仅以“根因相同”定义，也不能直接用向量分数生成真值。

- 冻结样本库、查询时间截面、评论、配置、模型和提示词；按票分组并优先时间切分。
- 当前票自身、同票历史、复制票和近重复簇不得跨训练与评测集合造成答案泄漏。
- 覆盖同车型不同功能、同信号不同异常、同名异义、跨车型兼容、未知字段、台架 / 实车及向量不可用。
- 分别统计标题查询与证据后查询；不能让旧策略看标题、新策略偷看事后人工答案。
- 初期建议至少 50 张查询票用于探索，最终验收样本量根据场景覆盖和统计不确定性确定，不能只报告合并均值。

### 8.2 指标与建议门槛

| 指标 | 统计口径 | 建议验收规则 |
| --- | --- | --- |
| Recall@20 | 前 20 条覆盖的相关案例数 / 候选库内全部相关案例数 | 配对对比旧策略，目标提高；提升幅度待基线后冻结 |
| Precision@3 | 前 3 条中的相关案例数 / 实际返回条数 | 不低于基线；空返回单独统计，不记作 100% |
| nDCG@3 | 依据人工相关等级评价前 3 条顺序 | 不低于基线，并检查各场景退化 |
| 冲突与泄漏 | 越权、明确不兼容、自身或评测答案泄漏的入选数 | 固定验收集必须为 0 |
| 空召回与覆盖 | 返回为空的查询比例、存在相关案例的查询覆盖率 | 与准确性一起报告，防止靠全部返回空刷指标 |
| 最终分析质量 | 相同当前证据下，人工盲审新旧结论 | 不降低正确率，不增加无证据断言 |
| 成本与延迟 | 召回 P50 / P95、请求体积、embedding 调用量、注入 Token | 先测基线，再确认预算；超预算不能默认上线 |

没有相关案例的查询不进入 Recall 分母，单独衡量是否错误注入；没有返回案例的查询也要保留在覆盖率统计中。相关性等级如何折算为“相关”、置信区间和最小提升门槛，应在正式对比前固定。

### 8.3 实施后的回归范围

- 单元测试：标识符标准化、中文词法、部分匹配、冲突、融合、去重、多样性、缓存失效和空结果。
- 集成测试：证据后可找回初次未命中的案例；精确匹配不被向量低分淘汰；超限、服务失败与取消可安全结束。
- 持久化与生命周期：同 run 的审计与案例身份保存、恢复、重跑历史、旧数据兼容，以及看板刷新后持久化。
- 按最终影响运行相关测试、typecheck、lint 和隔离构建；浏览器测试显式启用，记录跳过项。
- 离线检索评测、mock 流程、真实模型和真实工单验证分别报告，不互相替代。

## 9. 分阶段实施建议

| 阶段 | 最小交付 | 完成条件 |
| --- | --- | --- |
| P0：建立基线 | 固定查询与候选库、人工相关标注、现策略检索审计 | 可复现当前漏召回，并给出分场景基线 |
| P1：提高入口覆盖 | 中文词法、受控标识符标准化、独立精确召回、问题与答案分离 | 难负例回归通过，精确匹配不受语义门禁误删 |
| P2：证据后再次召回 | 有界样本快照、实际配置与 Evidence Packet 检索、恢复审计 | 可补回初次漏召回；超限与生命周期行为明确 |
| P3：校准与灰度 | 参数校准、固定评测对照、可回退策略开关 | 指标与成本达标，业务审核后再启用 |

不建议一开始就更换所有模型、引入新的存储服务或给所有字段设置固定权重。先确认漏召回来自候选入口、字段缺失还是排序错误，再决定下一步。

## 10. 审核事项与文档关系

实施前需确认：

1. 同规则组 / 同场景边界保持不变；跨车型仅在适用性有支持时参与。
2. 快照规模与请求大小上限，以及超过上限时接受何种覆盖限制。
3. 首期是否只使用现有信号字段，评论事实与异常模式是否分期加入。
4. 配置兼容性的判定来源；无可靠映射时只标记未知，不自动推定兼容。
5. 人工标注负责人、基线冻结方式、提升门槛与延迟预算。
