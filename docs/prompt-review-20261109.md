- 六个奇瑞规则组的六项提示词完全相同：chery D01-8255、chery-8155-others、chery T1YA-8255、chery T1J_FL3-8255、chery T1J-FL2-8255、T1L_FL1_8255。

## 3. 用户配置提示词逐项建议

第一组的六项提示词位于导出文件第 133～138 行；maxus 位于第 440～445 行；geely2 位于第 604～609 行。

### 3.1 信号提取：SIGNAL_EXTRACT_SYSTEM

**现状与风险：** 提示词含 `{问题描述}`、`{标题}`、`{model}` 等占位符，调查时的调用链未发现对应模板替换。当前显式输入主要为配置前 8,000 字符、评论正文及前一步需求。评论正文可包含标题，不能据此说标题完全未传入；明确的车型字段未单独提供。不同车型复制奇瑞电源信号规则，可能引入无关信号。

**建议：** 保留原始信号名及大小写，去重、一行一个；区分原文出现的信号和业务规则补充的信号。明确实际可用的标题、车型、映射来源，信息缺失时不猜。若需要模板变量替换或单独传入车型，应作为后续调用链调整，不应只改文案后视为解决。

证据入口：[signals-stage.ts](../src/server/pipeline/process/signals-stage.ts)、[prepare.ts](../src/server/pipeline/process/prepare.ts)。

### 3.2 需求提取：REQUIREMENT_EXTRACT_SYSTEM

**明确错误：**

- 输入“设置 `IHU_20_RgnSet=3` 强档”，示例答案却写成“`557909442` 值为1”。本建议要求纠正数值改写；属性 ID 映射也应依据当前配置另行核验。
- 风速/空调开关示例中，原文风速反馈 `CEM_IPM_FRONTBLOWSPDCTRLSTS_51A=9`、开关反馈 `CEM_IPM_FRONTOFFSTS_51A=1`；答案却把两项信号和值交换。
- 示例提前给出“是1说明vehicle已经透传，不是1说明vehicle有问题”，将待验证事项直接转为责任结论。

**建议：** 按“用户现象、操作、期望、待核对项”抽取，忠实保留信号、数值和原文约束。不要在需求阶段判断透传或责任模块。先逐条校验并修正示例，再考虑增加少量边界示例。

### 3.3 上层日志摘要：LOG_SUMMARY_SYSTEM

**现状与风险：** 要求信号名“全部英文大写，仅字母和下划线”，示例却含 `_471`、`_47C` 等数字，真实信号也存在 CamelCase。要求时间升序，但示例先出现 `16:48:16.348`，再出现 `16:48:14.357` 等更早时间。不同类型 ID 的一一对应要求过硬，可能丢掉无法映射但有价值的事件。

**建议：** 保留原始大小写，允许字母、数字、下划线；修正排序示例。分别表达包装属性 ID、VHAL prop ID、CAN 报文 ID，并注明映射来源。未知映射保留为未知，不静默删除所有未映射记录。

**流程限制：** 该提示词要求“只输出表格、不得解释”，但也被用于最终摘要兜底。最终结论任务需要缺口说明及结论格式，后续应区分阶段摘要和最终结论的调用契约。

证据入口：[log-summary-stage.ts](../src/server/pipeline/process/log-summary-stage.ts)、[conclusion-stage.ts](../src/server/pipeline/process/conclusion-stage.ts)。

### 3.4 Android/QNX 摘要：ANDROID_QNX_LOG_SUMMARY_SYSTEM

**现状与风险：** 提示词要求使用信号映射关系，实际该阶段主要收到 Android/QNX 日志，没有单独提供完整映射。输出要求“时间、模块、信号名、值”，示例第三列却为十进制或十六进制属性 ID。限制模块名单并排除 `signalApi-CarOperation`，可能遗漏关键链路证据。

**建议：** 分开记录信号名与属性 ID，未知项不补全；按链路价值筛选事件，保留上下行、错误、重复同值及关键边界事件。需要映射时，由调用方提供经配置核验的映射，避免模型凭记忆推断。

**当前边界：** 调查期间代码已加入 `signalHits <= 0` 时跳过该阶段；版本或 hash 元数据不应作为信号命中。本建议不将此前空日志调用行为视为当前仍存在的问题。

### 3.5 一致性分析：CONSISTENCY_SYSTEM

**强制结论需要审核：** 部分规则在 CAN 找到下设但缺少反馈，或者只有 VehicleService 下设打印却缺少总线证据时，仍要求输出“vehicle已经透传”。少量信号变化也被用于证明通路正常。建议分别说明已验证的上下行边界和未验证部分，再给流转建议。

若“vehicle已经透传”是固定转单口径，需要团队明确它究竟表示“下行已到总线”“某段软件处理完成”还是“完整上下行均正常”。本建议不擅自替换既有业务口径。

**固定信号污染：** 反馈缺失时要求写死 `ICC_SET_IPM_FirstBlowing`、`TMS_First_BlowingSts`、`TMS_11(0x448)`。建议从本票证据填入实际信号和报文；未观察到不能直接证明报文不存在或对手件未搭载。

**反馈判断建议：**

- 反馈不变可能是已达目标、重复同值或摘要只记录变化，不能直接等同于没有反馈。
- 请求值与反馈值可能采用不同枚举，应先依据映射转换，再比较。
- 反馈之后回0是否为正常复位或动作完成，应依据需求和枚举，不能无条件判正常。
- 一次配对成功后停止，可能遗漏同票后续失败操作；应覆盖全部关键操作后再汇总。

**时间判断建议：**

- “时间差≤30%”需要定义分母、比较对象与适用条件。
- 时间倒序不能取绝对值后直接判正常；跨时钟应先说明偏移假设和依据。
- “立即反馈”“例如0～2秒”“迟滞正常”需统一；阈值来自需求或配置，未知时不默认正常。
- 重复操作可能有多个匹配窗口，找到子序列不足以证明窗口唯一。
- 未找到窗口应区分日志截取不足、时钟未知、证据缺失与实际不一致。
- 用户规则禁止讨论时间戳/时区，而其他示例及内置约束允许时间对齐，应统一层级并明确偏移只是有依据的假设。

**输出与维护建议：** 用户提示词要求六部分，内置约束要求五部分，应统一为一份输出契约。移除重复转单句式、长分隔线和断句，如“如果下设信号下设值正常到总线，反馈信号”“信号没有没有反馈”。先修正语义，再精简长度。

### 3.6 CAN 对比：CAN_COMPARE_SYSTEM

建议与一致性阶段统一信号映射、方向、枚举及时间窗口口径。先确认事件属于哪次操作、数值是否可直接比较、时钟是否可对齐，再判断顺序、响应和一致性。多个候选窗口应保留歧义；缺少日志不能直接等同于链路故障。

## 4. 内置提示词及调用流程建议

| 场景 | 观察与风险 | 建议 |
| --- | --- | --- |
| 最终输出约束 | 用户六段格式与内置五段格式直接拼接 | 统一“现象、证据、根因、结论、置信度”等契约；允许根因尚无法确定；信号和窗口放证据段 |
| 实车场景提示 | 仅按场景加入“vehicle通路正常”预设 | 场景只决定检查重点，通路结论依据当前证据；调整需确认业务口径 |
| 多草稿聚合 | 聚合主要收到草稿，没有原始证据；多数一致可能重复同一错误 | 提供原始证据或可核验编号，保留争议，不能将多数一致当成验证 |
| 复核 | 原始证据、前序分析、最终结论及历史错误例混合输入；截取可能遗漏关键段 | 标明证据与待审结论，按关联性选案例，明确截断；保留 PASS/FAIL 合同，关键判断无法验证时不应 PASS，并说明缺口 |
| 自批判 | 时间、数值、信号名出现并不证明因果及模块归属 | 保留已有事实护栏，并检查推断链、映射、事件配对和责任归属；历史样本不能当本票证据 |
| 自动分类 | 示例缺少平台时仍默认8155，或按名称猜8255，与无法确定留空冲突 | 以显式证据或已确认配置为准，未知留空，不从示例隐含默认平台 |
| 聊天 | 记忆和知识库资料拼入 system，来源边界不够明确 | 标为参考资料，内部指令不作为系统指令执行；注明来源和日期，冲突时说明；不能声称执行未发生的后台操作 |
| 长期记忆 | 用户与助手对话一起抽取，可能把助手推测当成事实 | 仅保存用户明确确认内容，区分目标与事实，不将单票临时结论视为长期事实 |
| 信号自校验 | 候选名称不足以判断方向和具体语义 | 不确定时返回空匹配；后续可补充方向、描述和映射来源 |
| OCR | 数值误补可能污染后续证据 | 看不清时标注未辨认，不猜数字；相对其他问题优先级较低 |

## 6. 通用证据约束示例（待审核，不直接替换现有提示词）

> 只依据当前工单提供的材料作判断。保留原始信号名、数值和时间戳，不自动补全缺失映射或车型信息。区分直接证据、推断和证据缺口；每项通路及责任结论说明依据和已验证范围。未观察到反馈不等于反馈不存在，单段链路成功不等于全链路正常。证据不足时明确说明缺少什么。历史案例仅作为检查参考，不能作为当前工单事实。

该约束适合作为共同原则。各阶段仍应保留自己的输出契约，例如信号提取只输出信号列表、日志摘要输出事件、最终分析输出结论；不要把全部阶段强制改成同一格式。

## 7. 后续验证建议

建议固定 20～30 张具有人工确认结论的历史工单，对原提示词与经审核后的候选提示词做 A/B。保持模型、参数、输入证据与裁剪策略一致；若同时改变输入流程，应单独记录，避免将全部收益归因于提示词。

| 样本场景 | 重点检查 |
| --- | --- |
| 正常完整上下行、真实超时或值错误 | 是否正确区分正常与异常，结论是否覆盖全部关键操作 |
| 重复同值、反馈已处于目标值 | 是否误判为未反馈 |
| 请求与反馈采用不同枚举 | 是否直接比较原始数字而误判 |
| 缺 CAN、缺上层日志、截断材料 | 是否明确缺口，避免强制透传或归责 |
| 多次操作、多候选窗口、跨时钟偏移 | 是否保留因果顺序和匹配歧义 |
| 正常瞬态回0、真正异常回0 | 是否依据需求判断 |
| 车型未知、相似信号名、映射缺失 | 是否猜平台、补信号或误归属 |

指标建议：信号漏提与误提、数值改写、无依据透传结论、错误责任归属、缺口表达、复核误放行与误驳回、输入/输出 Token、耗时。准确率指标应提前明确人工真值和分母；证据不足案例不应为了通过率强行判定。
